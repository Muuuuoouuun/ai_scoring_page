## 제안 1 — P0: 상세 첫 화면에서 평가의 의미와 표본을 읽게 한다

현재 평가 영역은 기능·제약 뒤에 있고, `sample`을 ‘사용자 평가 N명’으로 표시한다. 그러나 `sample`에는 점수를 입력하지 않은 후기 계정도 포함될 수 있고, 각 축의 유효 응답 수는 `count`다. API가 반환하는 `latest`는 후기 `updated_at`이며 실제 사용일이 아니다. 두 숫자와 날짜를 별개의 의미로 보여줘야 한다.

**화면 변경안:** 도구 소개 다음에 작은 평가 요약을 두고 ‘사용자 경험 · 모든 업무/선택 업무 · 모든 플랜/선택 플랜’, ‘집계 대상 후기 N건’, 각 핵심 항목의 ‘응답 M건’, ‘후기 갱신일’을 표시한다. 점수가 없으면 짧은 평가 없음 상태와 확인된 공식 기능·활용법으로 이어준다. 직접 평가 상태는 별도 제목 아래 둔다. 상단과 상세 평가가 같은 응답 데이터를 사용하도록 한다.

항목별 응답 1–4건에는 실제 건수와 ‘소수 응답 평균’을 동반하고, 0건은 `미평가`로 표시한다. 5건 경계는 초기 표시 정책 제안이며 통계적 신뢰도 기준이 아니다. 5건 이상이어도 대표성·검증된 성능을 주장하지 않는다. 막대·색·종합 점수만으로 판단하게 하지 않는다.

조건 변경 중에는 이전 점수가 새 필터 결과처럼 보이지 않도록 요약·막대를 로딩 상태로 전환한다. 현재 `ToolReviews`는 이전 `scores`를 유지하고 `aria-busy`만 바꾸므로 시각적으로 이전 수치를 읽을 수 있다. 오류의 ‘다시 불러오기’는 현재 `location.reload()` 대신 평가 영역만 재조회하는 안을 검토한다. 후기 전체 목록 링크는 ‘관련 후기’라고 부르고, 집계 범위가 일치하는 조회가 생기기 전에는 ‘이 점수의 근거’라고 부르지 않는다.

**모바일·접근성:** 320/390px에서 요약의 조건·건수가 잘리지 않고 수치와 상태가 텍스트로 읽혀야 한다. 화면 읽기 상태 발표는 ‘조건 변경 → 조회 중 → 선택 조건의 결과’ 순서로 한 번씩 전달한다. 11–12px 보조 글과 작은 링크는 가독성과 터치 크기를 재검토한다. 핵심 조작의 44×44 CSS px는 제품 목표로 삼는다.

**검증 기준:** 후기 3건 중 1건만 특정 축 점수를 입력한 합성 로컬 데이터에서 3건을 그 축의 분모로 표시하지 않는다. 0/1/4/5건, 빈 조건, API 실패, 늦은 이전 응답을 각각 확인한다. `latest`를 최근 사용일·테스트일로 부르지 않는다. 비회원이 점수의 종류·표본·조건을 설명할 수 있는지 형성 평가에서 관찰한다.

관련 파일: `site/components/ToolReviews.tsx`, `site/app/api/scores/route.ts`, `site/app/tools/[id]/page.tsx`, `site/app/globals.css`. 최초 P0는 현재 응답으로 가능한 표시와 상태에 한정한다. 분포·사용일 범위·동일 집계 원문은 신규 데이터 계약이 필요하다.

## 제안 2 — P1: 비교를 같은 질문에 답하는 모바일 화면으로 바꾼다

현재 비교는 개별 도구의 기능 목록을 한 행 안에 나열한다. 기능명이 서로 달라 같은 기능의 차이를 사용자가 찾아야 한다. `.compare-table`은 최소 650px이고 좁은 화면은 가로 스크롤에 의존한다. 이는 현재 존재하는 동작이며, 페이지 넘침 결함이 있다는 뜻은 아니다.

**화면 변경안:** 상단에 비교하는 업무와 도구별 플랜을 표시하고 ‘핵심 차이 → 공통 기준 → 사용자 경험 → 출처’ 순으로 구성한다. 데스크톱은 공통 기준 행을 가진 표, 모바일은 ‘기준 제목 → A/B/C의 도구명·값·조건’이 반복되는 세로 묶음을 제공한다. 도구 1개만 있으면 선택 부족 안내와 관련 후보 추가를 제공한다. 2개부터 읽을 수 있고 세 번째는 선택 사항이다.

공통 기준은 검수한 기능 ID/대응표를 먼저 만든 뒤 적용한다. 원문 이름을 문자열로 맞추거나 목록에 없는 기능을 `미지원`으로 바꾸지 않는다. ‘차이만 보기’는 정규화된 행에서만 동작하며 미확인 값을 차이로 확정하지 않는다. 사용자 점수는 업무가 같고 각 도구의 플랜·표본이 표시되는 경우에만 나란히 읽게 한다. 표본 차이가 큰 평균의 우열 배지·색상 승자는 만들지 않는다.

**모바일·접근성:** 핵심 비교는 좌우 이동 없이 읽을 수 있어야 한다. 상세 원문 표를 유지하면 키보드 진입·표 제목·행/열 관계·내부 가로 이동을 보존한다. 도구명을 각 묶음에 반복해 기억 부담을 줄인다.

**검증 기준:** 2개/3개, 서로 다른 플랜, 한 도구의 미확인 기능, 무점수·소수 표본을 확인한다. 320/390px와 실제 200%에서 도구명·조건·출처·교체 행동에 도달한다. 사용자에게 같은 목적의 차이 1개와 확인해야 할 조건 1개를 찾게 하고, 실제 분자/분모와 시간을 기록한다. 기능 대응표가 준비되기 전에는 기존 원문 비교를 보존한다.

관련 파일: `site/app/compare/page.tsx`, `site/components/ToolUI.tsx`, `site/components/Shell.tsx`, `site/lib/catalog.ts`, `site/app/globals.css`. 단계형 화면부터 검증하고 공통 기준 데이터 확장과 분리한다.

## 제안 3 — P1: 후기 작성은 세 단계로 나누고 기존 복구를 보존한다

현재 한 화면에는 글 종류·도구·닉네임·관계·제목·업무·플랜·사용일·선택 점수 5개·본문·공개 동의가 모여 있다. 과거 390px QA 이미지에서도 단일 열의 긴 폼을 확인할 수 있다. 입력 부담이 크다는 것은 검증할 가설이며 현재 이탈률을 측정한 결과는 아니다.

**화면 변경안:** 1단계는 업무·플랜·사용일, 2단계는 했던 일과 좋았거나 막힌 점 한 줄 및 선택 점수, 3단계는 게시 카드 미리보기·닉네임·관계·공개 동의다. 제목·본문의 현재 필수 정책은 유지하고, 도구명/업무 기반의 중립적 제목만 수정 가능한 제안으로 제공한다. 본문 의견은 자동 생성하지 않는다. 점수는 설명 있는 선택과 ‘판단 어려움’을 제공하며 후자는 축 생략으로 저장한다. 새 안내를 기존 점수에 소급 적용하지 않고 입력 기준 버전이 필요하다.

상세의 필터는 후보로 전달하고 사용자가 실제 사용 맥락을 확인한다. 현재 기본값인 오늘을 실제 사용일로 조용히 확정하지 않는다. 날짜가 기억나지 않으면 일반 경험 글로 전환할 수 있고 점수 집계에서 제외됨을 설명한다. 모르는 플랜은 미확인으로 보존하고 특정 플랜의 응답에 넣지 않는다.

비회원은 입력·미리보기 후 로그인하여 3단계로 복귀하고, 동의를 다시 확인한 뒤 직접 게시한다. 기존 초안 필드에 단계·진입 맥락·버전을 추가할 때 도구·글 종류 간 충돌을 검토한다. 현재 키는 도구/글 맥락을 중심으로 하며 새 단계와 글 종류를 독립적으로 보관하는 계약은 없다. 같은 탭 임시 보관 범위만 약속한다.

**복구 의존성:** 현재 서버는 새 `id()`를 생성하므로 서버 수락 뒤 응답 유실 재시도에서 중복 게시를 막는 계약이 없다. 3단계 UI와 자동 재시도는 별개다. `submissionId`를 계정에 묶어 결과를 조회하는 서버 계약이 생기기 전에는 안전한 자동 재시도를 약속하지 않는다. 기존 버튼 잠금·연결 실패 시 입력 유지도 계속 필요하다.

**모바일·접근성:** 단계 변경 때 제목으로 초점을 옮기고 뒤로 가면 입력을 유지한다. 키보드가 열렸을 때 현재 입력·오류·다음 행동에 도달하며 고정 비교 바와 작성 바가 겹치지 않게 한다. 라디오 그룹으로 만든 점수 선택은 키보드 이동·선택값·설명 연결을 검증한다. 공개 미리보기는 색이나 위치만으로 공개 범위를 설명하지 않는다.

**검증 기준:** 후기/일반 글/답글의 기존 흐름, 단계 뒤로 가기, 다른 도구 전환, 로그인 취소·성공, 저장소 실패, 세션 만료, 연결 단절, 서버 수락 뒤 응답 유실을 구분해 검사한다. 입력 유실·로그인에 따른 자동 게시 0건, 서버 계약 도입 후 같은 제출 ID의 글 1건을 요구한다. 작성 시간은 실측 후 보고하고 ‘30초 완성’ 같은 약속은 쓰지 않는다.

## 제안 4 — P1: 홈의 작은 발견 카드에 확인한 차이와 정보 시점을 붙인다

홈의 검색·업무 링크·정보 우선 순서는 기획 v0.6과 일치한다. 현재 6개 도구는 고정 선정이고 카드에는 소개·분류·요금이 있다. ‘최근 공식 업데이트’의 목록은 게시일을 표시하지만 상세에서 제공하는 확인일·제공 상태·직접 실행 미등록 정보는 목록에서 바로 읽기 어렵다. 역사적 QA의 내용 점수 100을 10월 3일의 모든 정보가 최신이라는 증거로 쓰지 않는다.

**화면 변경안:** 도구 목록 위나 첫 목록 안에 검수한 발견 카드 최대 3개를 둔다. ‘확인할 질문 한 줄 → 무엇이 다른지 한 줄 → 콘텐츠 종류·확인일’ 구조로 가이드·비교·공식 변경에 연결한다. 실제 사용자 경험이 있을 때만 경험 관점 카드를 제공한다. 공개 정보만 읽고 나갈 수 있고 개인 도구 등록을 요구하지 않는다.

소식 미니 카드에는 실제 콘텐츠에 필요한 베타/단계적 제공 등 핵심 상태와 확인일을 간결하게 표시하고 상세에서 적용 대상·공식 원문·직접 확인 여부를 읽게 한다. 매일 검수 운영이 생기기 전 ‘오늘’, 실제 데이터 없는 ‘인기·급상승’을 사용하지 않는다. 43개 카탈로그 항목과 현재 소식 날짜는 파일에서 확인했지만 제품 발표 사실의 외부 재검증은 이번 UI 검토 범위가 아니다.

**모바일·접근성:** 검색을 첫 행동으로 유지한다. 카드 전체 클릭 가능 여부와 제목 링크의 초점이 일관되고, 상태·날짜가 작은 배지에만 의존하지 않아야 한다. 가짜 콘텐츠로 빈 공간을 채우지 않고 검수 항목이 1개면 1개만 보여준다.

**검증 기준:** 비회원/로그인 홈 모두 정보 탐색으로 열린다. 개인 데이터 0건이어도 검색·가이드·뉴스·비교 경로가 성립한다. 콘텐츠 0/1/3개에서 빈 상태·출처·날짜를 확인한다. 날짜 지난 행사가 예정 기회로 표시되지 않는다. 방문자에게 카드가 공식 요약·편집 큐레이션·사용자 경험 중 무엇인지 설명하게 한다.

관련 파일: `site/app/page.tsx`, `site/components/ToolUI.tsx`, `site/app/news/[id]/page.tsx`, `site/lib/content.ts`, `site/data/catalog.json`. 뉴스/기능별 확인일을 독립적으로 관리할 필요가 커지면 현재 도구별 `latestUpdate` 1개 구조와 별도 콘텐츠 모델을 후속으로 검토한다.

## 제안 5 — 후속: 기능 발견 허브는 독립된 검수 콘텐츠로 출시한다

9월 16일 문서는 기능 허브·기능 상세·8개 서비스·약 80–100개 기능을 정의했다. 현재 HEAD에는 해당 라우트와 데이터가 없다. 도구 카탈로그 확대나 `kind='feature'` 제안을 기능 리뷰 완성으로 보고하지 않는다.

**화면 변경안:** `/features`는 목적형 검색 → 지금 볼 기능 → 숨은 기능 → 목적별 묶음 → 전체 필터다. 카드는 공식명·한국어 이름·한 문장 가치·목적 최대 2개·핵심 조건 최대 2개·확인일을 보여준다. 상세는 쓰임·예시·시작 방법·플랜/기기/지역/제공 상태·출처를 먼저 읽게 한다. 직접 실행하지 않았으면 ‘직접 실행 확인 전 · 공식 문서 정보’, 실행했으면 날짜·환경·입력·관찰 결과를 별도로 표시한다. 편집 리뷰와 사용자 후기는 합산하지 않는다.

**출시 의존성:** 공식 출처·독립 확인일·상태·기능 ID·같은 목적의 대응 관계가 먼저 필요하다. 베타/단계적 출시/종료 상태를 구분하고 문서 충돌은 미확인으로 남긴다. 기능별 후기 ID와 집계 범위도 별도 설계한다. 공개 범위를 줄일 경우에는 9월 16일 문서의 첫 공개 수량과 다른 결정임을 사용자와 명시적으로 합의한다.

**모바일·접근성·검증 기준:** 필터가 URL과 동기화되고 검색 결과 없음에서 선택 조건·초기화를 제공한다. 도구 상세↔기능 상세 이동, 공식명/별칭 검색, 기능 후기와 도구 점수의 분리, 출처/확인일 누락 차단을 확인한다. 허브의 검수 운영을 준비한 뒤 구현 계획으로 전환한다.
