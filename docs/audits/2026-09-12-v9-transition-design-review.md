## 1. 먼저 고정할 계산 의미

### 날짜 네 종류

| 날짜 | 의미 | 기본값/검증 |
|---|---|---|
| 비교 시작일·종료일 | 양쪽 현금흐름을 합산하는 동일 구간. 양끝 포함 | 시작 today, 종료는 기존 horizonEndDate로12개월. 직접 날짜 지원. 시작≤종료 |
| 계산 기준일(asOf) | 어느 시점의 기록과 조건을 보고 비교했는지 | 서버/화면의 한국 날짜, 저장 시 고정 |
| 변경 적용일 | 새 플랜/서비스가 이용 조건을 제공하기 시작하는 날 | 다음 갱신일을 제안하되 직접 확인. 새 시나리오는 과거 적용을 실제 변경으로 기록하지 않음 |
| 새 계약 첫 청구일·주기 기준일 | 돈이 나가는 일정 | 적용일과 별개. 선결제·체험이면 서로 다를 수 있음. 실제 달력 주기를 사용 |

일할 계산을 하기 위한 날짜로 오해하지 않게 한다. 적용일과 첫 청구일 사이를 임의 비례 계산하지 않는다. 제공사 견적이 있는 경우에만 별도의 날짜·금액 행으로 입력한다.

비교 시작일이 과거여도 이미 확인한 결제/환불은 양쪽의 공통 기록이다. 사용자가 지금 검토하는 변경안은 과거 기록을 다시 쓰지 않는다. 과거 변경을 확인한 경우는 기존 ‘조건 이력/결제 기록’ 흐름에서 먼저 기록한다.

### 출력 세 층

1. **입력한 과거 결제·환불(양쪽 공통)**: 선택 기간 안의 확인 기록. 원래 결제/환불 날짜·통화로 보여준다.
2. **유지안/변경안의 앞으로 예상되는 순지출**: 앞으로 남은 청구와 확인된 정산 조건을 각 날짜에 반영한다.
3. **예상 차이 = 유지안 향후 순지출 − 변경안 향후 순지출**: 같은 통화끼리만 계산한다. 과거 공통액을 양쪽 전체 전망에 표시할 수는 있지만 절약액의 근거로 삼지 않는다.

비교기간 밖에서 이미 낸 선결제가 기간 안의 예정 청구와 연결되어 있으면, 그 예정 청구도 다시 더하지 않는다. 원금은 비교기간 안으로 옮기지 않는다. 과거 미확인 청구는0이 아니라 `확인 필요`이며, 이를 임의로 확정 미래 지출에 옮기지도 않는다.

## 2. 필요한 최소 입력: 기존 기록은 자동 표시하고 새 가정만 받기

### 기본 영역

| 입력/표시 | 최소 형태 | 이유 |
|---|---|---|
| 대상 계약 | 계약 선택. 서비스명·플랜·계정 별칭·번들 포함 도구 표시 | 같은 서비스의 복수 계약 구분, 번들 중복 방지 |
| 비교 기간 | 시작일·종료일 +3/12개월 빠른 선택 | 양쪽 같은 날짜, 월수 곱셈 방지 |
| 변경안 | 유형(주기/플랜/좌석/할인/대안), 이름, 선택적 catalog toolId | 한 계약 안의 변경 의도 식별 |
| 변경 적용일 | 날짜 또는 미확인 | 적용일 미확인은 시나리오 초안으로 보관; 실행 가능한 안으로 확정하지 않음 |
| 새 청구 조건 | 회당 금액·통화·주기·첫 청구일, 필요한 경우 주기 기준일/N개월 | 월/연 이외 기존 지원 주기도 유지 |
| 필수 기능·한도 | 현재 requiredFeatures/사용 목적을 미리 채운 짧은 설명 + `충족 확인/부족/미확인` | 체크 하나를 누르지 않으면 계산 자체를 막기보다 숫자는 가정으로 보여주고 적합 판정만 제한 |
| 선결제 여력 | 금액 또는 미확인, 통화 표시 | 빈칸은 무제한/충족이 아님. 비교 숫자는 보여주되 실행 가능 여부는 미확인 |

현재 계약의 amountBasis/seats/taxStatus/pricingMode/remainingPayments/remainingFromDate/knownFrom/termsHistory와 가까운 청구는 기존 기록에서 읽어 표시한다. 이를 유지안 입력으로 다시 타이핑시키지 않는다. 유지안에 다른 조건을 가정하려면 실제 계약을 편집하는 대신 비교 안에서 가정임을 명시한다.

### ‘전환 조건’ 상세 영역

| 입력 | 최소 표현/규칙 |
|---|---|
| 변경 뒤 기존 계약에 남는 청구 | **추가 청구 횟수(number\|null), 그 횟수를 세기 시작할 기존 청구일**.0은 없음 확인, null은 미확인. 기존 약정 잔여와 겹쳐 쓰기 위해 남기는 청구를 포함한다. 해당 날짜별 금액은 기존 조건 이력에서 계산해 사용자에게 목록으로 확인시킨다. |
| 기존 계약 이용 종료일 | 날짜 또는 미확인. **청구 종료일과 별개**다. 이미 선결제한 이용 기간을 표시하는 필드이며 자동 비용 행을 만들지 않는다. |
| 새 계약 이용 시작일 | 변경 적용일과 같으면 추가 입력 없음. 다르면 명시한다. |
| 할인/체험 | 첫 금액, **정상가가 처음 적용되는 청구일**, 정상 회당 금액, 자격 `해당없음/충족/미충족/미확인`, 출처·확인일. 갱신가 미확인이면 해당 날짜 이후 청구를 unknown으로 둔다. |
| 가격·세금 기준 | 총액/좌석당+좌석수, 세금포함/별도/미확인, 필요한 별도 세액. 표시한 회당 총액과 별도세액을 중복 더하지 않는다. |
| 전환/추가 청구 | 종류, 금액·통화, 발생일, 없음확인/금액확인/미확인, 근거. 데이터 이전·위약금·제공사 확인 일할정산 등을 소수 날짜 행으로 입력. 학습 부담은 메모이며 임의 금액화하지 않는다. |
| 환불 | 원 결제 선택 또는 근거, 확인 금액·통화, 반영 예정일, `없음확인/확정예정/이미기록됨/미확인`. 이미기록됨이면 기존 payment ID를 참조하고 금액을 다시 더하지 않는다. |
| 잃는 기능/변경 부담 | 짧은 메모. 필수 기능 미충족이면 비용이 낮아도 적합안으로 표시하지 않는다. |

`기존 잔여·중복 청구 합계`라는 하나의 금액만 받아 다시 더하는 현재 방식은 날짜별 비교에서 제거하거나 명시적 추가 비용 예외로만 남긴다. 알려진 기존 청구 목록을 먼저 보여주고, 그 목록에 없는 제공사 정산만 추가 행으로 받는 것이 중복 방지에 유리하다.

원 계약에서 이미 remainingPayments가 확인된 경우 이를 기본값으로 유지한다. 변경 가정에서 줄이려면 실제 면제/환불 정책을 확인한 별도 가정이 있어야 한다. 단순 새 서비스 선택만으로 기존 약정 의무를0으로 만들지 않는다.

## 3. 이용 겹침과 돈의 겹침을 구분

- 이용 겹침: 새 이용 시작일≤기존 이용 종료일이면 그 날짜 구간을 보여준다. 이 구간의 길이 자체는 금액이 아니다.
- 추가 기존 청구: 변경 뒤에도 실제로 예정된 기존 청구 이벤트만 변경안에 남긴다.
- 이미 낸 연요금: 공통 과거 기록이다. 남은 이용 기간이 겹쳐도 다시 비용에 더하지 않는다. 남은 달 수만큼 환불을 자동 계산하지 않는다.
- 기존 계약 이용 종료와 마지막 청구 날짜는 다를 수 있다. 잔여 청구는 종료 뒤에도 남을 수 있으므로 이용 종료일로 청구를 무조건 잘라서는 안 된다.
- 기존 계약이 이미 종료/해지되어 유지안의 예정액이0인 경우, 필요한 기능을 비교 종료일까지 제공하는지 따로 확인한다. 이용 종료 후 서비스가 없는0원 안을 적합한 유지안으로 자동 추천하지 않는다. 갱신 유지가 필요한 가정이면 비교 안에서 사용자가 확인한다.
- 약정 잔여 횟수와 기존 이력의 요금/통화/주기 변경이 있으면, 각 청구일에 맞는 버전을 이용한다. 잔여 전체를 현재 금액×횟수로 단순 계산하지 않는다.

## 4. 계산 구성과 확인 상태

한 선택 계약의 양쪽 모두 `billingIdentity`로 묶고, 결제 매칭은 `occurrenceKey`와 저장된 planned snapshot을 사용한다.

```
공통 과거 기록 = 선택기간 안의 기존 확인 결제 − 기존 확인 환불

유지안 향후 순지출[currency]
  = 유지안의 미지급 예정 청구
    + 유지해도 발생하는 확인된 추가 비용
    − 유지해도 받을 확인된 미래 환불

변경안 향후 순지출[currency]
  = 변경 적용 전의 공통 미지급 예정 청구
    + 변경 후 기존 계약의 확인된 잔여 청구
    + 새 계약의 예정 청구
    + 변경에만 발생하는 확인된 추가 비용
    − 변경에만 받을 확인된 미래 환불
```

수수료/환불에는 양쪽 공통인지 변경에만 발생하는지 구분이 필요하다. 기존 원장에 이미 입력한 환불을 변경안에만 넣으면 절감액을 부풀린다. 기본은 명시적 변경안 비용이며, 이미 원장에 있는 실제 기록은 양쪽 공통으로 자동 분류한다.

유지안과 변경안에 동일한 기존 청구가 있으면 같은 event key를 보존하되 양쪽 결과는 따로 계산한다. 서로 다른 시나리오에 존재하는 같은 이벤트를 하나로 합쳐 버리지 않는다. 변경안 안에서 기존 원장 매칭분과 새 시나리오 row가 중복되지 않게 식별자를 구분한다.

`금액 비교 가능`, `기능 적합`, `자격 충족`, `선결제 가능`, `날짜/정산 조건 완전`은 다른 상태다. 하나의 complete boolean에 기능·금액·자격을 숨기지 않는다. 하나라도 필요한 조건이 미확인이면 확인된 항목만 잠정 합계로 보여주고 `조건 충족 최저가/확정 절약액/실행 가능한 선택` 문구를 쓰지 않는다. 기능 미충족/자격 미충족은 명확히 부적합이며, 알려진 저렴한 숫자는 참고로만 남긴다.

`unknownTax`, `unknownHistory`, `pendingTerms`, `unknownRemaining`, `unknownDates`, 사용량 추가청구 등 기존 계산 경고는 시나리오 결과에도 전달해야 한다.0건은 없음 확인일 때만 완전한0이다.

### 선결제액과 기간 총액

현재 transitionComparison은 연 첫 청구에 **기간 전체** 잔여·전환비용을 더해 upfront를 만든다. 날짜가 생기면 이를 그대로 유지하지 않는다.

- 새 첫 결제액과 날짜를 별도로 보여준다.
- 같은 날 기존 청구/전환 수수료까지 준비해야 하면 같은 날짜의 양수 청구를 합한 `그날 준비할 금액`을 표시한다. 이를 한도와 비교한다면 같은 날 합계라는 보수적 기준을 명시한다.
- 필요하면 선택 기간의 가장 큰 날짜별 양수 청구 합계도 표시한다.11월의 비용을10월 첫 선결제에 무조건 합치지 않는다.
- 환불은 미래 예정 입금이므로 선결제 한도에서 자동 차감하지 않는다. 입금 순서까지 가정하지 않는다.
- 한도 미입력은 미확인. USD 청구와 KRW 한도를 환산 근거 없이 비교하지 않는다.
- 첫 신규 청구가 비교 시작일 전이면, 비교기간 밖 선결제액을 반드시 따로 표시한다. 기간 안 비용만 보고 ‘무료/더 저렴한 전환’으로 오해하지 않게 시작일 조정 안내를 한다. 비교기간 밖 필수 선결제를 숨긴 채 적합한 절약안으로 확정하지 않는다.

### 다른 통화

원통화별 합계/차이를 기본으로 한다. KRW 유지안과 USD 변경안이면 KRW+USD를 더하거나 금액 숫자끼리 빼서 단일 절감액/승자를 만들지 않는다. `통화가 달라 총액 우열은 미확인`으로 두고 선결제도 각 통화로 표시한다. 환산을 제공한다면 사용자가 확인한 환율·기준일·출처, 반올림 방식을 함께 저장하고 표시에서만 계산한다. 원 계약/실제 지급액을 변경하지 않는다. 이번 최소 구현에서 임의 환율을 도입할 이유는 없다.

### 수수료/환불/일할정산

- 카드 정산 총액에 이미 포함된 feeAmount를 다시 더하지 않는다. 원장 actualTotals(settlement=true)의 기존 의미를 따른다.
- 변환 수수료·위약금은 지급일에 비용으로 넣는다. 제공사 확인 견적이 총액이면 그 안의 부분 수수료는 설명용이다.
- 환불은 원 결제에 연결하고 실제/확정 예정 반영일에 차감한다. 조회기간 밖이면 기간 합계에는 제외하고 별도 날짜로 보여준다.
- 환불 미확인은0으로 확정하지 않는다. 없음 확인은0이다. 미래 확정 환불도 아직 실제 입금 원장으로 생성하지 않는다.
- 미사용 기간의 일할 반환, 남은 할인 유지, 과금일 변경을 자동 가정하지 않는다.

## 5. 저장·소유권·실제 기록 보존

새 비교는 독립적인 비공개 시나리오로 저장하는 것이 적절하다. 기존 saved comparison에 넣으려면 명시적인 금융 subtype과 링크 분기가 필요하다. 현재 구조에서는 `transition_comparison` 같은 별도 private_records kind가 의미와 validation을 분리하기 쉽다. 명칭은 구현 선택이며, 기존 도구 비교를 바꾸는 결정은 아니다.

최소 저장 내용:

- schemaVersion/calculatorVersion, 제목, 계산 기준일, 비교 시작·종료일.
- 원 계약 ID, billingIdentity, historyId/revision. 선택한 번들 전체라는 표시.
- 입력 가정: 변경안 조건/적용·청구 날짜/잔여 기존 청구/이용 종료일/할인·자격/추가 비용·환불/필수 기능 확인/선결제 한도.
- 결과 snapshot: 양쪽 날짜별 이벤트·원통화별 합계·누락/부적합 이유·예상 차이. 계산 당시 사용한 관련 조건/결제 참조 및 필요한 snapshot을 함께 보존하여 당시 결과를 확인할 수 있게 한다. 전체 과거1000개 이력을 무조건 복제할 필요는 없다.
- 가격·정산 근거와 확인일. 출처가 직접 입력이면 `직접 확인한 조건`이라고 표시하고 시스템 검수 공식 가격으로 격상하지 않는다.
- 사용자 결정: `검토중/현재유지/보류/관심없음/조건수정`과 이유. 사용 결과는 별도 메모. 값이 낮다는 이유로 사용자 결정을 자동 선택하지 않는다.

서버는 선택 계약과 참조 결제가 해당 계정 소유인지 조회한다. 사용자 입력의 userId나 임의 DB payload를 신뢰하지 않는다. snapshot을 저장할 때 받은 source historyId/revision이 달라졌다면 재계산/옛 조건으로 저장 중임을 명확히 처리한다. 이후 원장 revision이 달라지면 기존 비교를 몰래 바꾸지 않고 `저장 후 원 기록이 변경됨 · 현재 기록으로 다시 비교`를 보여준다. 새 계산은 옛 결과와 구분해 저장한다.

저장·수정·삭제는 비교 기록에만 적용한다. 계산 실행/공식 관리 페이지 이동/‘변경 검토’ 선택은 구독 조건, 해지 기록, 실제 결제/환불을 생성하지 않는다. 사용자가 실제 변경을 확인했을 때 기존 TermsEditor/결제 기록 흐름으로 이동하여 적용일·다음 금액을 명시적으로 저장한다. 확인한 변경/예상 비용 차이/원장으로 확인한 비용 변화는 서로 다른 상태다.

MyWorkspace는 Savings에 records와 저장 후 refresh를 전달하고, 저장한 금융 비교 목록을 해당 비교 화면에서 열도록 연결한다. owner GET/export/account DELETE는 새 kind를 포함하는지 검증한다. 현재 generic export와 account DELETE는 private_records 전체를 다루므로 구조상 재사용 가능하다. 저장된 결과의 ‘절약액’을 실제 누적 성과나 배지로 합산하지 않는다.

## 6. 원 명세를 확인하는 작은 검증 사례

아래 값은 모두 가상이며 검증용이다.

1. **공통 과거 결제**: 기간9/1–12/31, 기준일9/12. 기존9/1결제20,000원, 이후10/1·11/1·12/1각20,000원.10/1부터 새 연192,000원, 잔여 기존0/추가비용0/환불0. 공통과거20,000원, 유지향후60,000원, 변경향후192,000원, 향후차이−132,000원. 과거를 포함해도 차이는 같으며20,000원을 환불처럼 빼지 않는다.
2. **같은12개월/선결제 제한**:10/1–다음9/30, 월20,000원vs연192,000원. 유지240,000원/변경192,000원/차이48,000원. 한도100,000원이면 기능 충족이어도 연안은 선결제 조건 미충족이다.
3. **겹친 이용과 남는 청구**:9/12–12/31, 기존9/15부터매월20,000원. 새10/1연192,000원, 변경 후 기존10/15한 번 추가 청구, 기존 이용종료10/31. 유지80,000원, 변경은9/15공통예정20,000+기존잔여20,000+192,000=232,000원.10/1–10/31 이용 겹침은 별도 기간 표시이며 일수×임의단가를 더하지 않는다.
4. **선결제된 이용 겹침**: 기존 연요금은1/1실제 지급, 이용 종료12/31, 이후 잔여 청구0.10/1새 서비스로 변경해도 기존 연요금을 다시 overlap 비용에 넣지 않는다. 환불 근거가 없으면 남은3개월을 반환액으로 만들지 않는다.
5. **할인 종료**: 새 월요금10/1·11/1각10,000원, 정상가 최초 청구12/1부터20,000원.10–12월40,000원. 정상가가null이면 처음두 회20,000원은 확인된 예정액,12월1회는미확인, 확정 승자없음.
6. **기록된 환불 중복 방지**: 원장에11/2환불5,000원이 이미 있으면 양쪽 공통 실제 기록으로 한 번만 반영한다. 변경안의 확인환불 입력에서 같은 ID를 고르면 다시 차감하지 않는다.
7. **환불 시점과 한도**: 첫 연 결제10/1 192,000원, 확인환불11/1 20,000원. 기간순지출172,000원일 수 있지만10/1 준비금액은192,000원이다. 환불이기간종료뒤면 기간총액에서는 제외한다.
8. **다른 통화/세금미확인/기능손실**: 각각 숫자를0으로 메꾸거나 단일 승자를 만들지 않는다. 원통화별 합계와 구체적인 확인할 항목을 표시한다.
9. **번들·실제 연결**: 같은 billingIdentity의 두 구성원이 있어도 유지/잔여 청구는 한 번. 다른 조회기간에 지급한 실제 결제가 이번기간 예정일과 연결되어 있으면 해당 예정액은 다시 더하지 않는다.
10. **날짜 경계**: 월31일/2월말/윤년/기간종료일 당일 청구, 연 첫 청구가기간끝전인지후인지, 할인 정상가 적용일 당일을 검증한다. 월환산액×개월수로 대체하지 않는다.
11. **저장과 실제 원장 분리**: 비교 저장/보류/관리 페이지 링크를 누른 후 subscription/payment/cancellation/H payload는 byte-identical이어야 한다. source revision 변경 시 저장된 과거 결과가 자동 바뀌지 않는다.

이 범위는 원 명세의 한 계약 비교를 구체화한다. 검수한 대안의 공식 기능·요금 정보 공급은 기존 카탈로그/검수 흐름을 연결하며, 이 설계 문서의 가상 금액을 실제 제안 가격으로 사용하지 않는다.
