## 제안 회귀 입력 — 5개

| # | 입력 | 앱 이름과 무관하게 고정할 의미 기대값 | 현재 실행 관측 |
|---|---|---|---|
| 1 | 고객에게 보낼 보고서 초안을 작성하고 문장을 다듬고 싶어요 | 같은 기능/사용 사례에 문서 결과물과 작성·초안·퇴고 행동이 있어야 작성 근거가 된다. ‘프로젝트 진행 상황을 보고서로 확인’만 있는 기능을 작성 근거로 제시하지 않는다. | 상위 근거는 ‘글 작성·수정’, ‘공동 문서’, ‘여러 단계 업무 처리’, ‘Research’. Jira의 ‘보고서·대시보드’는 결과에서 빠졌다. 작성과 현황 조회의 핵심 분리는 반영되었다. |
| 2 | 프로젝트 진행 상황을 보고서와 대시보드로 확인하고 싶어요 | 진행 상태·업무 흐름을 모아 확인하는 근거는 유지한다. 작성 행동이 없다는 이유로 이 질의를 빈 결과로 만들거나 문서 작성 앱만 남기지 않는다. | Jira ‘보고서·대시보드’가 1위 근거로 남았다. 해당 기능의 설명은 정확히 ‘프로젝트 진행 상황과 업무 흐름을 보고서로 확인합니다.’이다. 현황 조회를 함께 제거하는 회귀는 관측하지 않았다. |
| 3 | 기존 보고서를 읽고 핵심 내용을 요약하고 싶어요 | 입력 자료인 문서/보고서를 읽기·분석·요약하는 행동과 프로젝트 현황 조회를 구분한다. ‘보고서’ 명사 일치만으로 현황 대시보드를 문서 요약의 직접 근거로 올리지 않는다. | **잔여 정밀도 문제:** Jira ‘보고서·대시보드’가 1위(41.5)이고 Mistral 자료 조사·문서 작업이 다음(32.4)이었다. Jira의 그 기능에는 문서 입력·읽기·요약 근거가 없다. 현재 변경은 작성 행동을 제한했지만 문서 읽기/요약까지 구분하지 않는다. |
| 4 | 보고서 작성 말고 프로젝트 현황을 대시보드로 조회하고 싶어요 | 부정된 작성 행동을 긍정 가산점으로 사용하지 않는다. 긍정 현황 조회는 보존한다. ‘보고서’라는 단어 때문에 문서 카테고리 전체 또는 현황 보고 기능을 임의 제외하지 않는다. 행동 제외를 해석하지 못하면 미적용 사실을 그대로 표시한다. | positive는 ‘프로젝트 현황을 대시보드로 조회하고 싶어요’, `unresolvedExclusions`는 `["보고서 작성"]`. Jira 현황 근거가 유지된다. 현재는 정확한 행동 제외를 적용했다고 주장하면 안 되지만, 부정된 구절이 긍정 점수에 섞이지 않는 경계는 유지된다. |
| 5 | 프로젝트 진행 현황을 확인하고 보고서 초안도 작성하고 싶어요 | 현황 확인과 문서 작성의 두 의도를 보존한다. 두 기능이 각각 근거를 가진 도구는 둘 다 제시할 수 있다. 한쪽 기능만 있는 후보를 두 작업 모두 지원한다고 단정하지 않는다. 두 기능을 반드시 같은 feature 한 개에서 찾아야 한다는 과도한 제한도 피한다. | Jira/Asana는 현황 관련 근거로, Claude는 작성 관련 근거로, ClickUp은 ‘공동 문서’와 작업 관련 근거로 남는다. 현재 `subjects.some`은 한쪽 관련성으로 후보가 되는 구조다. 결과 포함 자체를 실패로 삼지 말고, 실제 제시하는 근거가 어느 의도를 충족하는지로 판정해야 한다. |

## 일반 규칙과 시험 경계

- 문제는 제품 종류보다 **대상과 행동의 결합**이다. `보고서`를 무조건 글쓰기의 동의어로 보거나, `프로젝트`가 있다는 이유로 작성 의도를 무시하는 규칙은 피한다. 작성/문서 읽기·요약/현황 조회를 각각 해당 기능의 이름+설명 또는 실제 사용 사례에서 판정한다.
- 카탈로그에 이미 구별 가능한 근거가 있다. ‘글의 초안을 만들고 표현과 구성을 다듭니다’, ‘팀과 문서를 작성…’, ‘심층 조사 보고서를 만듭니다’는 작성 쪽이며, ‘진행 상황…보고서로 확인’, ‘보드의 진행 상황을 위젯으로 모아 봅니다’는 현황 조회 쪽이다. 이 구별을 category/앱 ID 예외로 구현할 이유는 없다. 이는 현재 카탈로그 문구의 의미 비교이며 이번에 공급사 기능을 새로 검증한 결과는 아니다.
- 위 입력의 시험은 결과 첫째 앱을 고정하기보다 **제시한 matchedFeatures가 요청 행동을 뒷받침하는지**, 현황 조회 입력에서는 해당 근거가 사라지지 않는지, 부정 구절이 positive에 남지 않는지로 작성하는 편이 낫다. 합성 최소 fixture가 필요하면 문서 작성 전용·현황 조회 전용·둘 다 지원하는 도구를 기능 문구로 구성하고 이름/ID/배열 순서를 바꿔도 같은 의미 판정이 유지되는지 확인한다.
- 출력한 feature의 `status`, `condition`, `sourceUrl`는 원본을 보존한다. 예를 들어 Research의 플랜별 한도, 대시보드의 연결 보드 수/플랜 조건을 작성/조회 적합성 점수로 무료 이용 보증으로 바꾸면 안 된다. 관련 기능 존재와 특정 플랜에서의 사용 가능성은 별개다.
- 현재 범위에서 새로 확인한 구체적 잔여 문제는 **3번의 문서 요약 vs 현황 보고 혼동**이다. 4번은 미해석 제외를 정직하게 남기는 기존 제한, 5번은 복수 의도에서 부분 관련 후보가 생기는 기존 구조다. 이 둘을 자동으로 새 확정 버그나 모든 기능 지원의 증거로 확대하지 않는다.

## Root의 읽기·요약 보완 계획에 대한 보존 조건

- 제품명 검색: 현재 카탈로그의 정확한 `name`/alias만 입력하는 탐색은 작업 행동이 생략되어도 해당 도구를 찾을 수 있어야 한다. 이 불변량은 위 다섯 목적 질의와 별도로 현재 제품명을 데이터에서 가져와 검증한다. 이름 일치는 ‘그 제품을 찾았다’는 근거이며, 이름 뒤에 요청한 미지원 기능까지 확인했다는 근거는 아니다.
- 현황/읽기: 2번의 프로젝트 진행 상황 조회는 그대로 남기고 3번의 문서 읽기·요약과 분리한다. 현황 보고 기능을 카탈로그에서 삭제하거나 ‘보고서’가 있는 기능을 일괄 차단하는 방식은 부적절하다.
- 기능 제목도 의미 근거다. 이름이 ‘문서 초안’ 또는 ‘문서 요약’처럼 대상과 목적을 이미 명시한다면 설명에 같은 동사가 반복되지 않아도 인정할 수 있다. 반면 ‘보고서·대시보드’라는 이름만으로 문서 작성/요약을 인정하지 않는다. `feature.name + feature.description`을 한 근거 단위로 읽되, 다른 무관한 feature의 ‘만들기/요약’ 동사를 빌려오지 않는다.
- 사용 사례도 보존한다. ‘문서 분석’, ‘글쓰기·퇴고’처럼 목적이 명시된 useCase는 의미 근거가 될 수 있다. 관련성을 얻은 useCase/feature만 각각 `matchedUseCases`/`matchedFeatures`에 남겨야 하며, 문서 요약 질의에서 ‘메일 초안’을 요약 근거로 끼워 넣는 것은 피한다.
- 위 항목은 아직 적용되지 않은 보완의 검증 조건이다. 최초 실행 관측을 GREEN으로 바꾸거나 재실행한 것으로 기록하지 않았다.
