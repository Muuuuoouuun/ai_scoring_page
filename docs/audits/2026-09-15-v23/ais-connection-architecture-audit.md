# 실제 계정 연결의 최소 통합 경계 — 읽기 전용 검토

확인일: 2026-09-15 (Asia/Seoul). 대상: `/Users/bigmac_moon/dev/ai_score/site`의 현재 소스와 테스트 하네스. **사용자의 최신 지시에 따라 실제 계정 연결·구현·승인 요청은 보류했다. 이 문서는 재개 시 참고할 설계 메모이며, 연결 기능이 구현되거나 검증되었다는 증거가 아니다.** Site, 데이터베이스, 환경, 운영 서비스는 변경하지 않았다. 실제 환경값·비밀키를 읽거나 공급사를 호출하지 않았다.

## 2. 최소 구조 제안 — 파일명·테이블명·환경 이름은 아직 제안

- `lib/connections.ts`: 소유권·상태 전이·연결별 동시 실행 권한·안전한 응답 객체를 한곳에서 관리한다. 공급사별 허용된 API 주소/필드/스코프는 별도 adapter로 둔다. 임의 사용자 URL로 인증 헤더를 전송하지 않는다.
- `lib/connection-crypto.ts`: 서버 전용 암호화/복호화만 담당한다. 설치된 Vinext의 `server-only` 지원 기록은 확인했지만 실제 모듈 경계는 구현 후 빌드에서 검증해야 한다. 파일 이름만 `.server.ts`로 바꾸는 것을 보호 수단으로 간주하지 않는다.
- 연결 전용 API: 인증된 목록 GET, 시작/해제/수동 동기화 POST, 공급사별 callback GET. 기존 workspace 기록 저장 API에 OAuth 자격증명을 통과시키지 않는다.
- **연결 테이블**: 무작위 ID, `user_id`, 공급사 ID, 검증된 외부 계정/워크스페이스 식별자, 연결 상태, 무작위 연결 세대(generation), 버전, 암호화 토큰 봉투, 만료/스코프, 실행 claim/기한, 마지막 성공 시각과 허용된 요약을 저장한다. 자격증명을 별도 테이블로 분리해도 되지만 최소한 `private_records`와는 분리해야 한다. 클라이언트 응답은 필드 허용 목록으로 작성하고 행 전체를 직렬화하지 않는다.
- **OAuth state 테이블**: 충분히 무작위인 state의 해시, 시작 사용자/공급사/연결 ID/세대, 정확한 callback URI, 생성·만료 시각, 소비 시각·claim ID, 필요한 PKCE verifier의 암호문을 저장한다. 임시 행도 삭제/해제 대상이다. 완료 commit이 끝날 때까지 claim 행을 권한 근거로 유지하면 계정 삭제와의 경합을 차단할 수 있다.
- 공급사 응답은 필요한 비민감 필드만 추려 개인 snapshot으로 저장한다. 전체 원문, 토큰 응답, authorization code를 저장하지 않는다. 성공/실패/부분 결과를 구분하고 실패 시 이전 성공 자료를 ‘최신’으로 표시하지 않는다. 현 단계에 수동 동기화만 있다면 별도 무인 스케줄러나 메일 연결은 필요하지 않다.
- 예시 환경 이름은 `CONNECTION_TOKEN_KEY`, 공급사별 `*_CLIENT_ID`/`*_CLIENT_SECRET` 등으로 정할 수 있으나 현재 이름이나 설정으로 오인하면 안 된다. 실제 공급사의 OAuth 방식·공개 클라이언트 여부에 따라 필요한 항목이 다르다. 암호화 키 누락·길이 오류는 연결 시작 전에 실패해야 한다.

토큰 암호화는 검증된 서버 암호화 방식(예: Web Crypto AES-GCM, 256비트 키)을 사용하고 매 암호화마다 새 nonce를 만든다. 사용자/공급사/연결 ID/봉투 버전을 AAD에 묶어 다른 계정의 암호문으로 치환할 수 없게 한다. key ID를 함께 두면 키 교체 경로를 만들 수 있다. 토큰·refresh token·PKCE verifier는 필요한 서버 요청 동안만 평문 메모리에 존재하며, 복호화 실패 시 평문 저장이나 암호화 우회를 하지 않는다. DB 암호화는 서버 키까지 침해된 상황을 해결하는 장치는 아니다.

## 3. 상태·경합·취소의 핵심 불변량

1. **시작:** 인증된 JSON POST에서 공급사와 요청 필드를 제한한다. callback/권한 부여 주소는 서버 설정에서 선택하고, 돌아갈 주소는 고정된 로컬 경로 또는 검증된 상대 경로만 허용한다. 연결 예약 행과 state를 함께 만든다. 새 연결 시도와 기존 정상 연결 유지 정책은 명시적으로 결정하되, 사용자가 새 승인을 취소했다는 이유로 기존 정상 자격증명을 우발적으로 지우지 않는다.
2. **브라우저·사용자 결합:** state를 시작 사용자와 묶고 해당 브라우저의 거래와도 연결한다. 짧은 수명의 Secure/HttpOnly cookie를 사용하는 경우 호스트의 callback·프레임·cookie 동작을 실제로 확인해야 한다. 사용자 ID 일치만으로 브라우저 거래 결합까지 검증했다고 주장하지 않는다. callback에서 로그인 문맥 또는 필요한 결합 정보가 없으면 안전하게 다시 시작한다.
3. **callback:** code/state 또는 공급사 error를 별도 엄격 스키마로 검증한다. 중복 query key, 과도한 길이, 잘못된 공급사, 이미 쓴 state, 만료 state를 거절한다. `expires_at > now`를 사용해 정확히 만료된 시각도 거절한다. 가능할 경우 공급사 공식 지원에 맞는 PKCE S256을 사용한다. 등록된 정확한 redirect URI와 공급사 분리는 OAuth 보안 권고와 일치한다. [OAuth 보안 권고](https://www.rfc-editor.org/rfc/rfc9700.html), [PKCE](https://www.rfc-editor.org/rfc/rfc7636.html)
4. **단 한 번의 소비:** state 조회 후 별도 무조건 UPDATE를 하지 않는다. 소유자·공급사·연결 세대·미소비·만료 조건이 모두 붙은 원자적 UPDATE로 claim하고 영향 행이 1개일 때만 code 교환을 시작한다. 두 callback 중 한쪽만 공급사에 나가야 한다. 교환 결과가 불명확하게 실패한 state를 재사용하지 않고 새 승인을 요구한다.
5. **늦은 결과 차단:** 네트워크 요청 후 token/snapshot commit은 현재 연결의 ID·소유자·세대·claim과 살아 있는 state 권한을 다시 조건에 넣는다. 해제, 더 최신 연결, 기록 삭제가 먼저 끝났으면 결과를 버린다. 네트워크 후 무조건 INSERT/UPSERT는 삭제한 데이터를 다시 만들 수 있으므로 사용하지 않는다. 같은 사용자가 다시 연결해도 새 ID/세대여야 옛 응답이 도달할 수 없다.
6. **D1 batch:** batch는 SQL 오류 시 rollback되지만 조건 불일치로 0행을 변경하는 것은 오류가 아니다. 따라서 첫 guard가 실패했는데 다음 INSERT가 진행되는 구조를 피하고 **모든 쓰기에 동일한 현재 권한 조건**을 적용한다. DB 트랜잭션 안에 외부 네트워크 대기를 넣지 않는다. [D1 batch 문서](https://developers.cloudflare.com/d1/worker-api/d1-database/)
7. **수동 동기화/refresh:** 연결별 단일 실행 claim과 버전 CAS로 병렬 refresh를 제한한다. 새 토큰이 저장된 뒤 늦게 온 옛 401/실패 응답이 연결을 끊거나 토큰을 덮어쓰면 안 된다. 회전하는 refresh token의 결과를 잃은 경우 공급사 계약 없이 자동 재교환하지 않는다. lease가 있다는 이유만으로 네트워크 호출의 정확히 한 번 실행을 보장한다고 주장할 수 없다. timeout·claim 만료·불명확한 결과 처리가 필요하다.
8. **해제·삭제:** 로컬 토큰 제거, state 무효화, 세대/진행 작업 무효화를 원자적으로 처리한다. 공급사 권한 취소 API가 있다면 지원 조건에 따라 별도로 처리하고, 실패했을 때 ‘외부 권한도 삭제됨’이라고 표시하지 않는다. 현재 ‘내 기록 삭제’ batch에 모든 신규 개인 테이블을 넣는다. 이미 출발한 네트워크 요청 자체를 되돌릴 수 있다는 약속도 하지 않는다.
9. **기존 기록 보존:** 연결된 서비스의 신원/워크스페이스 조회 성공으로 유료 플랜·실제 결제·할인 자격까지 추정하지 않는다. 공급사 동기화 자료가 사용자가 기록한 구독 금액, 계약 이력, 실제 결제/환불을 자동 덮어쓰지 않게 한다. 연결은 기존 서비스 등록과 관계를 맺을 수 있지만 그 등록 기록 자체가 접근 권한은 아니다.
10. **반환·로그:** callback 완료는 비밀 query가 없는 로컬 주소로 이동시키고 `no-store`와 referrer 보호를 적용한다. 브라우저용 연결 정보와 내보내기에 토큰 평문·암호문·state/verifier·client secret이 없어야 한다. 공급사 원문 오류도 로그/알림/개인 기록에 흘리지 않는다.

## 4. 현재 하네스로 반드시 고정할 동작 시험

`tests/api-harness.mjs`는 실제 모듈을 VM에서 로드하고 모든 Drizzle 마이그레이션을 메모리 SQLite에 적용한다. `h.user`, `options.now`, 가짜 fetch, 공유 가능한 `env.DB`를 이용할 수 있다. 기본 fetch는 외부 호출을 거절한다. 기존 알림/이메일 race 시험의 일시 정지 adapter를 재사용할 수 있다. 아래는 **시험 제안이며 이번 검토에서 실행하거나 통과시킨 시험이 아니다.**

| 범위 | 사전에 고정할 기대값 |
|---|---|
| 인증/소유권 | guest 거절. B 사용자가 A 연결 ID로 목록·동기화·해제·callback을 수행할 수 없음. body의 userId 무시. 두 사용자가 같은 외부 계정 ID를 가졌다는 이유로 서로의 행이나 존재 여부가 노출되지 않음. |
| 일반 변경 요청 | cross-origin JSON과 비 JSON 요청 거절. 임의 공급사/임의 token endpoint·callback URL·return URL 거절. 기존 workspace API 형태와 소유권 시험 유지. |
| state | 잘못된 값·다른 사용자/공급사/브라우저·중복 query·재사용·정확한 만료 시각에서 공급사 호출 0회. 유효한 한 번의 callback만 소비. 사용자 취소도 정해진 state 전이로 종결. |
| callback 경합 | 동일 state callback 두 개를 동시에 멈췄다 재개해 교환 호출 1회, 유효 저장 1회. 예외/불명확한 교환 후 같은 state 재시도는 다시 교환하지 않음. |
| 새 승인 대 옛 승인 | 두 연결 시도가 겹쳐도 명시된 최신 시도/기존 연결 정책대로 동작. 더 오래된 callback이 최신 계정·토큰을 덮어쓰지 않음. |
| 해제/삭제 경합 | 교환·refresh·sync의 응답 직전에 해제/‘내 기록 삭제’ 실행. 늦은 결과가 토큰/state/snapshot을 복구하지 않음. 같은 사용자 재연결 뒤에도 옛 응답이 새 연결에 기록되지 않음. |
| refresh 경합 | 정상 병렬 요청에서 refresh 단일 실행, 승리한 token 버전 보존. 옛 401/실패 도착이 새 토큰을 무효화하지 않음. lease 만료/timeout 뒤 불명확한 회전 토큰은 안전한 보류/재승인 정책으로 처리. |
| 암호화 | DB 평문 token 없음. 새 nonce 사용, 변조/다른 사용자 AAD/다른 key/key 누락 시 실패. 실패 시 plaintext fallback 없음. 키 교체 시 읽기/재암호화 정책 시험. |
| 출력/오류 | 목록·workspace·export·callback 이동 주소·로그 수집에 토큰/state/verifier/암호문 없음. 공급사 error body에 비밀 문자열을 넣은 모의 응답도 밖으로 전달되지 않음. |
| snapshot 의미 | 429/timeout/잘못된 JSON/불완전 pagination에서 무한 재시도하지 않음. 이전 성공 자료를 최신 완료로 바꾸지 않음. 스코프 부족·플랜 미제공을 무료/유료 확정으로 표시하지 않음. 기존 사용자 금융 기록 불변. |
| 마이그레이션/삭제 | 현재 migration chain에서 신규 schema 적용 성공. 기존 기록 payload/인덱스/내보내기 의미 불변. 한 사용자의 신규 연결 데이터만 삭제되고 다른 사용자의 데이터 보존. guard 0행일 때 후속 쓰기도 0행. |
| 설정/호스트 | 설정 불충분이면 시작 시 안전하게 비활성화되고 state/외부 호출이 생기지 않음. callback 인증 문맥 소실 시 재시작하며 다른 사용자에게 연결하지 않음. |

하네스 보완이 필요한 정확한 지점: `h.call`은 고정 `/api/test` JSON 요청/JSON 응답을 가정하므로 callback은 직접 `Request`로 호출해 상태 코드·Location·cookie를 확인해야 한다. `server-only`를 쓰면 테스트 로더에서 의도한 서버 환경 처리가 필요하다. VM에는 `crypto`, byte encoder와 URL이 있지만 새 코드가 요구하는 전역(`URLSearchParams`, base64 함수 등)은 현재 노출 목록과 맞춰야 한다. controlled clock은 state 만료와 claim/refresh 경합에 함께 적용한다. 모의 공급사 시험이 실제 호스트 OAuth 동작을 입증하지는 않는다.

## 5. 보류 상태와 재개 시 선행 확인

지금은 사용자 지시에 따라 코드나 연결을 추가하지 않는다. 재개 시에는 선택한 공급사의 공식 OAuth/PKCE/refresh/revoke·필요 스코프·조회 가능한 실제 계정/플랜 필드, 등록 가능한 HTTPS callback과 호스팅 인증 전달, 서버 비밀 저장 및 암호화 키 준비를 먼저 확인해야 한다. 특정 공급사·계정의 요금/구독 정보 API가 존재한다고 현재 소스만으로 가정할 수 없다. 위 메모는 그 선택이 정해졌을 때 기존 개인정보·계약·삭제 경계를 보존할 최소 방향을 설명한다.
