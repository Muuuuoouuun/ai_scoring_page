## 저장/사용자 확인의 연결

- `Savings.tsx`는 MyWorkspace의 records를 받아 한 billingIdentity를 선택한다. 금액·정상가·세금·좌석/사용량·기존 청구 및 이용 종료·날짜별 추가금액·필수 기능/전체 기간/자격/변경 의사/통화별 준비금액 입력이 엔진으로 연결된다.
- `CostComparisonResult.tsx`는 양쪽 날짜별 일정, 원통화 합계, 필요한 최대 같은날 gross액, unknown/부적합 이유, 비교기간 밖 준비액, 이용 겹침 일수를 설명한다. 이미 낸 이용 기간에서 환불/추가비용을 자동 만들지 않는다.
- `ComparisonConditions.tsx`는 저장한 입력 조건·원 가격 출처/확인일·추가금액·기능/현금 조건·저장 당시 원 계약 조건을 읽을 수 있게 표시한다.
- `/api/cost-comparisons`는 소유한 구독과 결제를 다시 읽어 결과/source snapshot을 서버에서 만든다. 원장 H UUID+revision 및 parent 존재를 INSERT SQL에서 검사한다. 클라이언트가 보낸 가짜 result는 사용하지 않는다.
- 저장은 별도 costComparison 레코드이며 financial rows는 byte-identical 테스트로 보존된다. annotation은 결정·이유·결과만 바꾸고 source/result를 유지한다. 과거 비교는 원장이 바뀌어도 자동 재작성하지 않는다.
- owner 조회/삭제/export/account erase 및 stale/ABA/계산후source변경/cross-origin/비로그인 거절이 API 테스트에 포함된다.

## 남은 한정된 제약과 중대성

- 먼저 선결제하고 나중에 이용을 시작하는 후보는 현재 firstCharge>=switchDate 제약 때문에 직접 표현할 수 없다. UI는 switchDate를 이용 시작·전환일로 표시한다. 이는 지난 설계 검토에서 밝힌 입력 제약이지만, 고정8.3.4의 명시된 한 계약 날짜 비교 사례를 미구현으로 돌릴 별도 새 게이트는 아니다. 표현 범위를 넓힐 때 날짜 의미를 분리하면 된다.
- 서로 별개인 환불이 우연히 같은 날짜/통화/금액이면 현재 중복 의심 검증은 보수적으로 보류한다. 임의로 한 번 더 빼서 잘못된 확정 절약액을 내는 문제는 해소되었다. 향후 별도 원 거래 연결/명시 구분은 개선 여지이며 이번 원문 게이트의 새 선행 조건은 아니다.
- keep coverage 검증은 canonical endDate와 전체 기간 fit 확인에 기반한다. 제공사 사용 권한을 자동 조회하거나 필수 기능 사용을 자동 검증하는 기능으로 해석하면 안 된다.

위 한계를 숨기지 않되, 이미 충족한 구현 게이트에 원문 밖 요구를 추가하거나 현재 미관찰 브라우저/운영 근거를 충족했다고 주장하지 않는다. Root의 실제 브라우저 QA 및 정확한 배포 결과는 별도로 기록해야 한다.
