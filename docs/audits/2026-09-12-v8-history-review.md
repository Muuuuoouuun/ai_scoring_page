## 3. 최소 데이터 구조

### 3.1 이력은 서버가 소유하는 완전한 조건 스냅샷

다음 모양이면 별도의 이벤트 소싱 체계는 필요 없다.

```ts
type Terms = {
  plan: string;
  amount: number | null; currency: Currency;
  amountBasis: 'total' | 'perSeat' | 'unknown'; seats: number | null;
  taxStatus: 'included' | 'excluded' | 'unknown'; taxAmount: number | null;
  pricingMode: 'fixed' | 'usage' | 'hybrid';
  personalShare: number | null; // 계약 회당 내 부담 예상액, 이 통화 기준
  cycle: Cycle; cycleMonths: number | null;
  anchorDate: DateOnly | null;
  firstDueDate: DateOnly | null; // 버전의 첫 확인 일정, 화면용 이동 커서가 아님
  status: ContractStatus; pauseBilling: PauseBilling;
  resumeDate: DateOnly | null; endDate: DateOnly | null;
  remainingPayments: number | null;
  remainingFromDate: DateOnly | null; // 잔여 N회를 세기 시작하는 기준
};
type TermsVersion = {
  id: string; recordedAt: string; // 서버 부여
  effectiveFrom: DateOnly | null;
  state: 'confirmed' | 'draft';
  terms: Terms;
  reason: string; sourceNote: string;
  supersedes?: string; // 오기 정정 시 이전 항목을 지우지 않고 참조
};
type TermsHistory = {
  schemaVersion: 1; revision: number;
  knownFrom: DateOnly; // 이 시점부터 보관된 조건으로 계산할 수 있음
  versions: TermsVersion[];
  legacySnapshot?: object; // 원 payload를 보존하는 최초 전환 근거
};
```

- `effectiveFrom`은 계약상 적용일, `recordedAt`은 이 사이트에 기록한 시각이다. 혼용하지 않는다. 적용일 단위는 기존과 동일한 한국 날짜이며 `validDate`를 사용한다.
- 스냅샷에는 적어도 계산 입력과 플랜명이 함께 들어간다. 요금 근거·필수 기능/권한 설명도 변경 플랜의 근거를 남길 필요가 있으면 같은 버전에 짧게 보존한다. 메모/별칭만 수정하는 경우 금융 버전을 만들지 않는다.
- `priceChangesAt/renewalAmount` 입력은 새 확정 버전을 만드는 단축 입력으로 전환한다. 별도의 가격 분기와 이력을 동시에 계산해 두 번 적용하지 않는다.
- `firstDueDate`와 잔여 횟수의 시작일을 보존한다. 이후 목록의 “다음 청구일”은 계산 결과다. 화면에서 다음 결제일이 넘어갔다고 과거 생성 시작점을 덮어쓰면 안 된다.
- 이력의 추가/정정/미래 변경 취소는 서버 작업이다. 클라이언트는 `expectedRevision`과 변경 제안만 보내며, 전체 과거 배열이나 `recordedAt/id`를 덮어쓸 권한을 갖지 않는다.

### 3.2 번들 저장의 작은 선택

단독 계약은 subscription payload 안에 이력을 둘 수 있다. 다만 같은 번들 여러 행에 서로 다른 사본이 생기지 않도록 해야 한다. **현재 구조에서 공통 처리를 가장 단순하게 하려면 기존 `private_records`에 내부 전용 `kind='billing_terms'`, `target=billingIdentity`인 JSON 레코드 하나를 두는 방식이 적합하다.** 기존 계정/종류/target 유일키를 쓸 수 있어 새 테이블이 필수는 아니다. 이는 저장 구현 선택이며 사용자 기능 추가가 아니다.

GET의 정규화 단계가 구독과 이력을 연결해 계산기에 전달한다. 일반 메모 저장은 이력을 교체하지 않는다. API가 금융 변경을 한 번 기록하고 같은 번들의 모든 화면이 그 원본을 읽는다. 내보내기/계정 삭제에는 이 내부 기록도 포함한다. 직접 `kind=billing_terms`를 넣은 일반 payload 저장은 허용하지 않는다.

기존 `billingIdentity`와 `plannedKey` 문자열은 유지한다. 이번 범위에서 이력이 있는 번들의 식별자 변경/합치기/분리는 계속 차단하고 별도 계약으로 기록하게 할 수 있다. 식별자 자체 변경 지원은 이 요구를 위해 필요한 추가 기능이 아니다. 이름 변경을 지원하려면 결제 식별자와 표시용 번들 이름을 분리해야 하며 기존 키를 재작성해서는 안 된다.

### 3.3 결제·환불별 실제 내 부담

```ts
// 기존 payment payload에 추가
personalAmount: number | null;       // 이 결제 또는 환불의 확인된 내 부담
personalCurrency: Currency | null;   // 금액이 알려진 경우 필수
// 예정 청구를 새로 연결할 때 서버가 고정하여 저장
plannedVersionId: string | null;
plannedCurrency: Currency | null;
plannedPersonalAmount: number | null; // 당시 확인된 예상 부담, 실제 값과 별도
```

금액은 기존과 같은 통화별 최소 단위 정수다. 실제 부담을 원통화로만 지원하는 더 작은 첫 구현이라면 `personalCurrency=payment.currency`로 명시적으로 제한할 수 있다. 다만 정산 통화로 알고 있는 개인 비용은 기록하지 못한다고 표시해야 한다. 이미 원통화/정산 통화를 구분하는 앱이므로 독립 통화 한 필드를 두고 통화별로 합산하는 쪽이 덜 혼동된다. 환율 자동 계산은 추가하지 않는다.

`null`은 미확인, `0`은 본인 부담 없음이 확인된 값이다. 현재 계약 부담액, 계약 총액 또는 좌석 비율을 실제 값으로 자동 저장하지 않는다. 예상 부담을 입력 도움값으로 제시하더라도 고객의 확인 없이 실제 기록으로 취급하지 않는다. 실제 개인 환불도 계약 환불 비율로 자동 계산하지 않는다.

## 4. 기존 기록과 마이그레이션 호환

1. 새 필드가 없는 payment는 `personalAmount=null`, `personalCurrency=null`로 읽는다. 실제 계약 총액·정산액·환불·`plannedKey/plannedAmount`는 그대로 보존한다. 초기값 0이나 현재 `personalShare`를 채우지 않는다.
2. 기존 구독은 최초 전환 시 원 payload를 보관하고 관측 기준일 `knownFrom`을 만든다. `created_at`이나 `nextDate`를 실제 최초 계약 적용일로 간주하지 않는다. 사용자가 기존 조건이 적용된 시작일을 확인해 입력하면 그 범위부터 날짜별 이력 계산을 지원할 수 있다.
3. 이력 시작 전 조회에서도 기존 실제 결제/환불은 정상 합산한다. 보관되지 않은 과거 조건을 새 가격으로 복원하지 말고 “계약 조건 이력 미보관”과 해당 불완전 범위를 표시한다. 기존 현재-조건 참고 계산을 남기더라도 역사적 실제 조건 계산과 명확히 분리한다.
4. 기존 `priceChangesAt`이 미래이면 현재 기준 스냅샷과 그 날짜의 후속 가격 버전으로 옮길 수 있다. 이미 지난 전환이라면 입력된 두 금액/날짜는 원형으로 보존하고 현재 금액은 기존 `contractAmount(c, knownFrom)` 의미로 정규화한다. 당시 좌석·세금 등까지 알았다고 가정해 완전한 과거 스냅샷을 만들지 않는다.
5. `anchorDate`가 비어 있는 기존 계약은 기존 API의 `anchorDate || nextDate` 호환 규칙을 유지한다. 월/분기/년의 1/3/12개월 해석과 수동 1회 규칙을 바꾸지 않는다.
6. 동일 번들 멤버의 기존 금융 조건이 일치하는지 정규화 후 확인한다. 충돌하면 첫 행/최근 행을 임의 선택하지 말고 조건 확인 대상으로 남긴다. 기존 “알려진 금액 멤버 우선” 규칙이 과거 조건 전체의 진실성을 보장하지는 않는다.
7. 최초 이력 레코드 생성은 유일키로 중복을 방지하고 재시도에 같은 결과가 나와야 한다. 실패 후 일부 멤버만 새 계산을 쓰는 상태를 피한다. 기존 `plannedKey` 유일 인덱스와 수동 SQL 마이그레이션 호환을 유지한다.

## 5. 날짜별 계산의 최소 규칙

- `termsAt(date)`는 활성 확정 버전 중 적용일이 해당 날짜 이하인 가장 최근 버전을 고른다. 미래 버전은 오늘의 월 환산/목록 금액을 바꾸지 않는다. 같은 적용일의 두 활성 확정 버전은 거절하고, 명시적 정정 관계만 허용한다.
- 유효 구간은 `[effectiveFrom, nextEffectiveFrom)`으로 나눈다. 각 구간의 주기·기준일·첫 청구일로 날짜를 생성하고 구간 밖 이벤트는 제외한다. 적용일 당일 청구는 새 조건이다. 금액뿐 아니라 좌석·세금·통화·상태·내 부담도 그 이벤트의 버전에서 읽는다.
- 가격이 10월 10일 바뀌고 원래 청구일이 15일이면 10월 15일에 새 가격을 적용한다. 10월 10일 추가 청구나 일할 환불은 만들지 않는다. 실제 추가 청구/환불은 고객이 별도 원장에 기록한다.
- 주기 변경은 새 적용일과 새 일정 기준을 명시적으로 확인해야 한다. 옛 일정은 적용일 이전까지, 새 일정은 확인한 첫 청구일부터 생성한다. 같은 계약/날짜 청구는 하나만 허용한다. 연간 선결제의 중간 요금 변경만으로 즉시 새 연간 청구를 만들지 않는다.
- 잔여 N회는 `remainingFromDate`부터 전체 일정에서 소진한다. 조회 시작일마다 N회를 다시 만들거나 가격 버전마다 N회를 초기화하지 않는다. 가격/좌석 변경은 같은 잔여 예산의 기준을 계승한다. 주기/잔여 약정 자체를 바꾸는 경우 새 잔여 기준을 명시적으로 확인한다.
- 중단/해지 이력도 해당 날짜 이후에만 적용한다. 확인된 잔여 청구는 이용 종료일만으로 삭제하지 않는다. `paused/unknown`과 별도로 확정한 잔여 N회 처리 등 현재 통과한 동작을 유지한다.
- 적용일 미확인 항목은 초안으로 보존하고 계산에 몰래 적용하지 않는다. 고객이 변경이 이미 발생했다고 확인했지만 날짜/가격이 미확인이면 마지막 가격을 계속 확정값처럼 보여주지 말고 영향 범위를 불완전으로 표시한다.
- 예정 연결은 날짜별 일정에서 검증한다. 과거 결제를 수정할 때 현재 통화와 비교하지 않고 해당 예정일 버전 또는 보존된 연결 스냅샷과 비교한다. 기존 연결을 유지하는 메모 수정이 새 버전 때문에 거부되지 않아야 한다.
- 실제 금액은 payment 원장을 실제 날짜로만 합산한다. 조건 이력을 정정해도 실제 금액/통화/환불일/연결 당시 예상 견적은 바뀌지 않는다. 필요하면 “현재 정정된 조건으로 계산한 값”과 “연결 당시 예상값”을 구분한다.
- 한 계산 결과를 MyWorkspace 요약, BillingReport, 예정 청구 선택지, 가까운 결제 알림에 재사용한다. 화면마다 raw subscription의 현재 필드로 계산하지 않는다. 합계에서도 안전 정수 범위를 확인한다.

## 6. 실제 개인 보기 계산과 수정 보호

전체 계약과 개인 보기의 계산 경로를 명시적으로 분리하되 같은 기간·같은 청구 연결을 사용한다.

- `personalActual`: 기간 내 결제의 알려진 `personalAmount` 합 − 기간 내 환불의 알려진 `personalAmount` 합. 각 항목의 `personalCurrency`별 버킷으로 합산. 미확인 결제/환불 건수를 별도로 반환한다.
- `personalRemaining`: 아직 연결되지 않은 미래 예정 이벤트의 **해당 날짜 버전** `personalShare` 합. 계약 전체 합계와 더하지 않는다.
- `personalForecast`: 위 두 값의 같은 통화 버킷별 합. 계약의 예정 이벤트가 결제와 연결되었다면 실제 내 부담이 null이어도 예정 개인액을 다시 더하지 않는다. 그 대신 실제 개인 부담 미확인을 보여준다.
- 계약 부담액이 바뀌어도 기존 결제의 개인 부담은 바뀌지 않는다. 원 결제와 환불이 다른 달이면 각자의 실제 날짜에 반영한다. 기간 순액이 음수인 것은 그 달 환불이 더 컸다는 뜻일 수 있으므로 0으로 잘라내지 않는다.
- 실제 개인 부담은 같은 통화로 비교 가능한 전체 결제액/정산액보다 클 수 없다. 통화가 다르고 환산 근거가 없으면 자동 환산 검증을 하지 않는다. 수수료가 포함된 정산 총액을 사용하면 수수료를 다시 더하지 않는다.
- 원 결제의 실제 개인 부담이 알려져 있으면 동일 통화의 누적 개인 환불은 그 금액을 넘을 수 없다. 원 결제 개인액/통화의 수정으로 기존 개인 환불과 모순이 생기면 먼저 정정하도록 거절한다. 전체 금액에 대한 기존 환불 제한도 유지한다.
- 원 결제의 개인 부담이 미확인이어도 확인된 개인 환불을 기록할 수는 있다. 원 결제 부담의 미확인을 유지하고 원장 전체가 완전하다고 하지 않는다. 원래 부담을 0으로 만들어 제한을 우회하거나 환불을 없애지 않는다.

## 7. 저장·수정에서 놓치면 안 되는 경계

1. 일반 저장이 과거 이력을 지우지 않게 서버가 기존 이력을 다시 읽고 병합한다. 스키마 기본값 때문에 생략된 history가 빈 배열로 저장되는 경로도 막는다.
2. `expectedRevision`을 저장 시 원자적으로 확인한다. 단순 SELECT 후 UPDATE는 동시 두 탭 저장을 막지 못한다. 조건 변경과 번들 공통 상태 저장은 충돌 시 전체가 실패해야 하며, 마지막 저장이 상대 이력을 없애면 안 된다. stale 응답은 409와 재조회 안내로 처리한다.
3. 이미 연결된 청구에 영향을 주지 않는 미래 조건 추가와 과거 조건 정정을 구분한다. 현재 주기/통화 차단을 일괄 해제하지 않는다. 새 날짜별 연결 해석이 검증되기 전에는 기존 제한을 유지한다.
4. 과거 버전의 단순 삭제는 금액 이력을 없앤다. 최소 UI는 이력 열람과 새 적용일 변경만 제공해도 된다. 오기 수정이 필요하면 기존 버전을 남기는 정정 항목을 추가하고, 영향을 받는 기간/연결을 확인한 후 반영한다.
5. cancellation 저장도 같은 조건 변경 함수를 사용한다. `confirmedAt`은 기록/확인 시점이고 실제 조건 적용일과 다를 수 있다. 기존 해지 기록만으로 알 수 없는 소급 적용일을 생성하지 않는다.
6. 계정 소유권을 이력 조회/추가 전에 확인한다. 다른 계정의 subscription, billing identity, version, payment/refund ID를 입력해도 조회/변경할 수 없어야 한다. 공개 카탈로그/검색/커뮤니티에 이력을 전달하지 않는다.

## 8. 필요한 최소 화면

- 구독의 “계약 조건 변경” 입력: 새 플랜/금액/현재 지원하는 추가 조건, 적용일, 변경 메모. 미래 적용이면 “예정 변경”으로 구분. 기본 구독 이름/개인 메모 편집과 분리하거나 저장 시 금융 변경 여부를 감지한다.
- 구독별 “조건 이력” 펼침: 적용일, 기록일, 변경 전후의 핵심 값, 미확인/정정 상태. 과거 이력 미보관 안내 포함. 과도한 분석 화면은 필요 없다.
- 결제/환불 폼: “이번 결제에서 내가 실제 부담한 금액 / 이번 환불 중 내가 받은 금액”, 통화, 빈칸=미확인, 0=부담 없음. 예상 부담은 참고값으로 별도 표시.
- 기간 보고서: “계약 전체 / 내 부담” 선택이 실제·남은 예상·전망·월별 합계에 함께 적용. 미확인 개인 결제와 이력 공백을 수치와 문장으로 표시. 기존 계약의 참고 개인 합계를 실제 내 부담 합계로 이름만 바꾸지 않는다.

계산/API 검증 뒤에는 부모가 실제 배포에서 최소 **조건 변경 전후 날짜 조회 → 저장 → 전체 새로고침 → 이력 재확인**, **실제 개인 결제/환불 저장 → 개인 보기 총액 확인 → 전체 새로고침**, **번들 한 번 집계와 테스트 자료 정리**를 수행해야 한다. 소스 검사나 단위 테스트만으로 화면 필드가 올바른 산술에 연결됐다고 판정하지 않는다.

## 10. 다음 구현 묶음과 점수 처리

1. 정규화·공통 이력/원장 타입·서버 소유 저장과 이전 기록 호환.
2. 날짜별 일정/조건 해석·안정된 기존 청구 연결·개인 원장 계산; H/P 경계 예시 검증.
3. 최소 조건 변경/이력/실제 개인액 UI를 같은 계산 결과에 연결; 요약·알림의 현재 필드 직독 제거.
4. 배포 후 저장·재조회·실제 예시와 계정 격리 증거 기록.

고정 게이트 **8.3.1–8.3.3의 기존 점수는 여기서 다시 가산하지 않는다. 8.3.4는 이력 외에도 유지된 상세 전환/겹침/환불 비교 범위가 함께 충족돼야 하므로 이번 구현만으로 PASS가 되지 않는다. 1.2.4 역시 전체 개인/운영 최소 범위의 포괄 게이트여서 그대로 별도 판정한다.** 이번 문서는 구현 제안이며 어떤 게이트의 신규 통과 증거도 아니다.
