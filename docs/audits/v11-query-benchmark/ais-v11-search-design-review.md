# V11 검색·추천 설계 독립 검토

검토일: 2026-09-12. 현재 `site/lib/catalog.ts`, `components/Recommend.tsx`, `Explore.tsx`, `GlobalSearch.tsx`, `useToolSearchMCP.ts`, `app/api/search/route.ts`, `tests/api.test.mjs`, 현재 20개 카탈로그와 V10 질의 벤치마크를 읽었다. 설계 의견서만 작성했으며 소스·운영·브라우저·Git·Sites·벤치마크 원본을 변경하거나 외부 서비스에 질의를 전송하지 않았다. 기능·가격 서술은 이미 보관된 카탈로그 근거의 사용 방법을 검토한 것이며 공식 가격을 이번에 새로 확인한 것으로 표시하지 않는다.

## 판단과 최소 범위

**제안된 로컬 토큰/업무 개념 검색 + 명시적 제외 분리 + 실제 기능 근거 출력 방향이 적절하다.** 가장 중요한 경계는 ① 제외 대상의 타입, ② 제품 플랜과 요청 기능의 조건, ③ 빈 질의와 해석되지 않은 질의, ④ 기존 검색 반환 형식·공개/개인 범위다.

대안은 세 가지다. 토큰 분리만 추가하면 가장 작지만 “문장을 다듬다/퇴고”, “폼에 새 문의/트리거”처럼 현재 기능과 표현이 다른 업무를 놓친다. 현재 기능·용례에 연결하는 작은 개념 사전까지 추가하는 안을 권한다. 큰 형태소 모델·임베딩·별도 LLM 추천 서비스는 현 카탈로그 규모와 이번 목표에 필요한 변경이 아니다.

현재 문제는 문장 길이 하나가 아니다. `catalog.ts:9–15`는 질의 전체 부분 문자열과 7개 트리거를 쓰고, 일부 확장어에 `slack/notion/cursor/copilot` 등 제품 이름이 직접 들어 있다. 부정 구간의 업무도 동일하게 확장하며, `Recommend.tsx:7`은 실제 매칭 이유와 무관한 앞의 두 용례를 출력한다. 이 세 경계를 함께 고쳐야 “결과는 생겼지만 이유가 틀린” 상태를 피한다.

## 1. 순수 검색 단계와 출력

권장 순서는 **정규화 → 제외 구간 추출 → 긍정 업무 해석 → 기존 범위 필터와 제외 필터 교집합 → 근거별 점수 → 안정 정렬**이다. 제외 구간에서 추출한 단어를 긍정 확장 입력으로 다시 사용하지 않는다.

- 이름·별칭·분야·용례·기능을 카탈로그에서 읽어 일관되게 정규화한다. Unicode 정규화, 영문 소문자, 반복 공백·구두점 처리를 쿼리와 색인에 함께 적용한다. 제품명과 별칭은 단어·구문 경계 및 한국어 조사 처리를 고려하되 `Gemini Notebook`을 짧은 `Gemini`보다 먼저 인식한다.
- 조사/어미 처리는 확인한 업무 어근과 제한된 형태를 대상으로 한다. 모든 한글 토큰 끝을 무조건 잘라 내는 규칙은 제품 이름과 보통 명사를 손상시킬 수 있다. `다듬고/다듬기`, `프로토타입을`, `마감일을`처럼 해당 어근을 보존하는 방법이 낫다. 빈번한 “하고 싶어요/도구/추천해주세요”만으로 결과가 생기지 않게 한다.
- 개념 사전은 `초안·제안서·문장 다듬기→글 작성/수정`, `상태·마감일·캘린더→업무 데이터 관리`, `새 문의·폼·앱 간 전달→입력/트리거/액션`처럼 업무를 연결한다. **업무→특정 제품 ID/이름 보너스**를 넣지 않는다. 새 제품이 같은 실제 기능을 갖추면 사전을 고치지 않고도 해당 업무에 참여할 수 있어야 한다.
- 정확한 제품명/별칭, 구체 기능, 실제 용례, 넓은 분야를 구분한다. 기능 일치 없이 `image` 분야라는 이유만으로 Figma를 “이미지 생성 기능이 맞음”으로 설명하지 않는다. 넓은 `개발`만 일치하는 배포 도구와 `코드 제안`을 직접 매칭한 편집 도구를 같은 강도로 올리지 않는다.
- 같은 단어의 반복이나 같은 개념의 여러 동의어가 점수를 누적시키지 않게 개념·근거 단위로 중복 제거한다. 평점·사용자 수·최신 업데이트 날짜는 이번 업무 관련도 점수에 섞지 않는다. 동점은 기존 이름 정렬과 명시적인 ID 보조 정렬 등 결정적인 기준을 유지한다.
- 다중 업무에서 일부만 매칭됐으면 실제 매칭된 기능만 보여준다. “초안 작성과 실시간 공동 편집”에서 초안 근거 하나를 찾았다는 이유로 두 작업을 모두 충족했다고 설명하지 않는다.

기존 `searchCatalog(query, options)`와 `Tool + relevance` 배열을 유지하면서 부가 근거를 더할 수 있다. 추천은 동일 검색 결과가 보유한 실제 feature의 `name`, `description`, `status`, **원문 `condition`**, `sourceUrl`을 사용한다. 결과와 별도로 동의어 규칙을 다시 실행해 이유를 만들지 않는다. 개념/적용 제외 목록을 함께 보여줄 필요가 있으면 동일 순수 해석 결과를 재사용한다.

제품명 검색에는 이름 일치 이유만 있어도 된다. 정확한 제품명 결과에 임의 기능을 매칭된 것처럼 붙이지 않는다. 용례만 일치한 경우도 “카탈로그 활용 예시”로 분리하고, 관계없는 기능의 공식 URL을 그 용례의 직접 증거처럼 붙이지 않는다. 기능이 `unknown`이면 확인된 지원 근거로 승격하지 않는다. 입력·원본 카탈로그 객체는 변경하지 않아야 한다.

## 2. 한국어 제외 구문의 경계

작은 문법으로 확실하게 인식한 제외만 적용하고 화면에 실제 해석한 조건을 짧게 보여주는 것이 안전하다. 필요한 타입은 `excludedCategories`, `excludedKinds`, `excludedToolIds`다. 제품 식별은 현재 이름·별칭을 기반으로 하고, 분야/유형은 기존 enum을 사용한다.

| 예시 | 권장 해석과 불변 조건 |
|---|---|
| 이미지 생성 말고 보고서 작성 | `image` 분야 제외, 긍정 업무는 보고서 작성. 이미지 기능도 가진 ChatGPT 전체를 제거하지 않는다. 이 의미는 기존 N1의 고정 기준과 동일하다. |
| 코딩 도구는 제외하고 개인 업무 정리 | `development` 분야 제외. 부정된 “코딩”으로 Cursor/Copilot/모델을 가점하지 않는다. 현재 `productivity`인 Linear까지 개발 관련 용례만 보고 임의 제외하지 않는다. |
| API 모델 말고 논문 자료를 읽는 앱 | `model` 제외. 모델 제공사의 앱까지 함께 제외하지 않는다. `앱`이 반드시 `ai-app` enum만 뜻하는지는 별도 명시 없으면 강제하지 않는다. |
| Notion 빼고 업무 정리 | 해당 제품 ID만 제외. 모든 생산성 SaaS를 제외하지 않는다. |
| Notion과 Slack은 제외하고 협업 | 연결된 두 제품 대상의 제외가 필요하다. 마지막 명사만 제거하는 정규식은 부분 처리 사실을 숨기지 않아야 한다. |
| 보고서 작성, 이미지 도구는 제외 | 제외가 문장 뒤에 와도 동일. 문장 전체를 지우는 탐욕적 패턴을 피한다. |
| 코딩뿐만 아니라 문서도 | 추가 의도다. `아니라`가 있다는 이유로 코딩을 제외하지 않는다. |
| Notion은 제외하지 말고 비교 | `제외`와 `말고`를 각각 독립적으로 잡아 Notion을 제거하면 안 된다. 이중 부정은 지원을 구현하거나 “제외로 적용하지 않음/조건 확인”으로 남긴다. |
| 로그인 없이, 코딩 없이, 무료가 아닌 | 제품/분야 제외와 다른 기능·비용 조건일 수 있다. `로그인`을 Supabase 제외로, `무료가 아닌`을 무료 요구로 바꾸지 않는다. 확인되지 않은 조건을 충족했다고 말하지 않는다. |

`말고/빼고/제외하고/제외한/아닌`의 단순한 단일 구문부터 지원하되 조사, 문장부호, 앞/뒤 배치, 알려진 대상 사이의 `와/과/및/,`를 테스트한다. `없이/안 쓰고/필요 없는`은 대상에 따라 의미가 달라지므로 무조건 동일 제외 문법으로 확장하지 않는다. 정확히 제품·분야·유형을 해석하지 못한 부정 구문은 긍정 가점에 재사용하지 말고 적용되지 않은 조건을 표시한다.

명시적인 선택 필터와 문장 제외가 충돌하면 결과는 빈 교집합이다. 예를 들어 category=image + “이미지 도구 제외”에서 필터를 몰래 완화하면 안 된다. 문장에 제외만 있고 알려진 대상이 있다면 남은 카탈로그를 조건 필터 결과로 보여줄 수 있지만 “업무 기능 일치”라고 이유를 만들지 않는다. 의미 없는 입력 `%`, 구두점만, 제거된 불용어만 있는 질의는 진짜 빈 입력과 구별해 0건으로 두는 편이 기존 계약과 맞는다.

## 3. 기능·플랜 근거의 정직한 표시

**`pricing`에 무료 플랜이 있다는 사실은 요청한 기능이 무료라는 증거가 아니다.** `Recommend`의 기존 “무료 플랜이 확인되었습니다”와 “조건에 맞는 선택지” 조합은 “무료로 그룹 허들” 같은 입력에서 오해를 만든다.

- 기존 무료 옵션은 제품 수준의 무료 플랜 필터라는 의미를 유지한다. 제품의 무료 플랜 여부, 요청 업무에 매칭된 기능, 해당 기능의 확인된 조건을 나눠 표시한다. 무료가 요청되면 예를 들어 “제품 무료 플랜 있음 · 요청 기능은 아래 조건 확인”처럼 범위를 밝힌다.
- Slack 허들에 실제로 매칭됐으면 바로 옆에 현재 `무료 플랜은 일대일 허들, 그룹 허들은 유료 플랜 기준입니다.`와 해당 sourceUrl이 보여야 한다. 이 경우 “무료 그룹 회의 조건 충족”으로 쓰지 않는다. 기존 C5는 이 구체적 경고 표시 또는 후보 제외 중 어느 쪽도 허용한다.
- 혼합 문장 안의 `무료`·`유료` 단어만 보고 기능 전체를 무료/유료로 분류하지 않는다. “무료 일대일/유료 그룹”과 “무료 사용량 제한”은 다르다. 현재 자유 서술형 카탈로그로 판정하기 어려우면 **조건 확인 필요**를 유지하고 원문을 제시한다. 명확한 별도 구조가 없는데 완전한 플랜 자격 판정기를 이번에 덧붙일 필요는 없다.
- 조건 문장을 그대로 검색 본문에 넣고 긍정 가점을 주는 것도 주의한다. “오프라인 미지원”의 `오프라인`, “무료 체험 없음”의 `무료`가 지원 근거가 되어서는 안 된다. 조건은 일치한 기능의 제한·설명 근거로 우선 사용한다.
- 현재 `pricing.includes('무료')`는 기존 데이터에서는 제품 필터로 쓰이지만 일반 규칙으로는 “무료 플랜 없음”도 통과한다. 변경 시 해당 부정 표현의 테스트를 두거나 명시적 제품 무료 상태를 별도 정규화한다. 검증되지 않은 제품 플랜 값을 새로 채우지 않는다.
- 한국어 옵션은 기존 `korean === '지원'` 계약을 지킨다. `확인 필요`를 관련도가 높다는 이유로 통과시키거나 무료 체크를 해제하지 않는다. 모델의 무료 API 한도는 앱의 무료 플랜과 같은 사용 경험이라고 설명하지 않는다.

## 4. API·화면·개인 범위 호환성

1. **기존 반환 계약 유지.** `Explore`, `Recommend`, 전체 검색 API, `useToolSearchMCP`가 같은 함수를 사용한다. 배열 반환을 `{results, interpretation}`으로 바꾸면 호출자가 모두 깨진다. 부가 메타데이터를 덧붙이거나 별도 순수 해석 함수를 공개하는 방식이 작다. 결과의 `relevance`는 숫자여야 하며 DOM 전용 값, 함수, Map/Set을 API 근거 필드로 직접 반환하지 않는다.
2. **서버 실행 가능성.** 검색 모듈은 catalog/순수 helper만 의존해야 한다. React, window/document, auth, D1, 네트워크 호출을 끌어오지 않는다. 클라이언트와 서버는 같은 입력·같은 카탈로그에서 같은 도구 순서를 반환한다.
3. **필터는 항상 교집합.** category/kind/free/korean/owned를 점수 계산 후 완화하거나 top6을 채우는 용도로 무시하지 않는다. `owned:undefined`는 제한 없음, `owned:[]`는 0건이며 두 상태를 합치지 않는다. 알 수 없는 owned ID는 결과를 만들어내지 않는다. 알려지지 않은 category/kind를 전체로 바꾸는 변경도 피한다.
4. **도구함 로딩.** 현재 Recommend의 owned 조회는 user 변경 시 이전 배열을 먼저 지우지 않고 취소 경계도 없다. 이번에 범위 설명을 강화한다면 `onlyMine` 활성 + 로딩/실패/로그아웃을 전체 공개 목록으로 폴백하지 않게 한다. user가 바뀌면 이전 조회 응답이 새 계정 범위를 덮지 않아야 한다. 개인 조회는 기존 `/api/workspace`에만 남기고 공개 search API가 개인 레코드를 읽도록 확장하지 않는다.
5. **전체 검색의 기존 의미.** `/api/search`는 q 160자, type allowlist, 빈 q의 빈 결과, `results/counts/total/partial`를 유지한다. `type='all'` 전체 건수를 먼저 계산하고 선택 유형만 반환하는 기존 counts 의미를 보존한다. 공개 published/nonreply 조건, LIKE escape, hidden/private 제외, 커뮤니티 오류의 partial=true도 그대로다.
6. **도구와 비도구의 해석 구분.** 현재 가이드·뉴스·행사·커뮤니티에는 새 제외 해석이 없다. 도구 검색만 바뀌었다면 전체 검색에서 모든 콘텐츠에 자연어 제외가 적용된다고 안내하지 않는다. 필요하면 “도구 결과에 적용한 제외 조건”이라고 한정한다. 도구의 더 큰 점수 상수가 공개 콘텐츠의 전체 정렬과 정확한 제목 검색을 밀어낼 수 있으므로 기존 정확 제목 API 테스트를 유지한다.
7. **입력 길이.** 전체 검색 API는 160자, MCP 검색은 200자, Explore/Recommend 입력은 현재 상한이 없다. 알고리즘의 안전한 처리 한도와 UI 상한은 정하되 API의 160자 계약을 몰래 바꾸거나 서버만 질의를 잘라 다른 의미를 만들지 않는다. 사용자 입력을 정규식 소스로 직접 삽입하지 않는다.

## 5. 구현 전에 고정할 테스트 경계

아래는 순위 숫자 상수나 구현 함수를 그대로 복제하는 테스트가 아니라, 외부에서 관찰할 수 있는 계약이다. 카탈로그 원문과 옵션 입력은 동결하고 전후 비교해야 한다.

| 경계 | 최소 관찰 가능한 기준 |
|---|---|
| 공백·대소문자·반복 | 동일 제품명/별칭의 대소문자·공백 변형은 같은 대상을 찾음. 같은 업무어 반복만으로 다른 후보보다 임의 승격하지 않음 |
| 긴 자연어 | 고정 D1/I2/P2/A2의 후보 누락을 재평가. 고정 기대를 출력 후 수정하지 않음 |
| 제외 | 앞/뒤 구문, 조사, 두 제품 제외, 분야/유형/제품 범위를 구분. 모든 결과에서 제외 대상을 제거하며 상위6만 검사하지 않음 |
| 부정 반례 | “뿐만 아니라”, “제외하지 말고”, “로그인 없이”를 단순 제외로 잘못 처리하지 않음 |
| 필터 단조성 | 같은 q에서 추가 필터 결과는 기존 결과의 부분집합. owned[]/unknown ID, 무료×한국어의 0건, category와 문장 제외 충돌 유지 |
| 이름과 조건 충돌 | 정확 제품명이라도 유료 제품+무료 필터, model+model 제외를 통과하지 않음 |
| 출처 연결 | 모든 matched feature가 해당 tool.features 원본에 존재하고 condition/sourceUrl/status가 보존됨. 임의 URL·관계없는 기능·unknown 지원 보장 없음 |
| 무료 기능 | C5의 허들 조건이 실제 추천 표면에 표시되거나 Slack 제외. 제품 무료 문구만으로 성공 판정하지 않음 |
| 복합 업무 | 일부 기능 매칭을 전부 충족으로 설명하지 않음. 미매칭 조건을 실제 지원으로 채우지 않음 |
| 빈 값 | 빈 Explore는 기존 목록; `/api/search?q=`는 기존 빈 결과; `%`/구두점뿐/일치 없는 질의가 전체 목록으로 확대되지 않음 |
| API 회귀 | 정확한 가이드/행사/뉴스 제목 검색, type별 결과·counts, hidden/private/LIKE wildcard 제외, DB 실패 partial 유지 |
| 동등성·부작용 | 같은 pure 함수가 서버/클라이언트에서 같은 결과. 검색 전후 catalog 객체·옵션·owned 배열 불변, 별도 외부 요청 없음 |

기존 `tests/api.test.mjs:22`는 `%`가 0건이어야 한다. 정규화 결과 빈 토큰을 빈 입력과 합쳐 전체 목록을 반환하는 변경은 이미 있는 테스트를 깨뜨린다. 첫 결과 3개만 적절한지 보는 기존 benchmark와, 제외/근거 보존처럼 모든 결과에 적용되는 새 불변량을 구분한다.

새 문장 표본은 출력 호출 전에 기대를 정하고 별도 파일로 보관한다. 예를 들어 “고객 안내문 문체를 고치고 짧게 만들기”, “화면 간 이동을 연결해서 팀원에게 시연”, “마감 날짜별 할 일을 달력으로 보기”, “문의 제출 때마다 다른 서비스에 새 항목 추가”, “문서 작업을 찾되 Notion과 Slack은 제외”, “개발뿐만 아니라 글 수정도”, “API 모델은 빼고 자료 인용을 확인”, “무료라고 해도 그룹 허들 조건을 확인”처럼 업무/표현/부정/조건 조합을 바꾼다. 이 예시는 **이번에 실행하지 않은 테스트 설계 제안**이며 공식 제품 기능 사실이나 실제 사용자 입력이 아니다. 일부 표본은 개발 중 튜닝에 쓰지 않고 첫 최종 실행 결과를 별도 보고해야 한다.

## 6. 기존 20개 벤치마크 재사용 시 주의

고정 cases SHA256 `322fb90697148e6b77a53e8de2ca720f4cfd3041433bfb882113aacca294bd9c`, 20개 입력·기대·최초 관측을 보존한다. 비교 결과는 V11 새 파일로 쓴다. 기존 cases를 수정해 성공 수를 올리거나 V10 관측 JSON을 덮어쓰지 않는다.

**기존 runner를 그대로 복사해 실행한 것만으로는 새 추천 UI를 평가할 수 없다.** 현재 runner는 `specificWarningInRecommendationSurface = false`를 고정하고 기존 정적 추천 이유를 문자열로 재현한다. 함수 import도 `catalog.json` 하나만 허용하므로 새 순수 helper 파일을 분리하면 runner가 실패할 수 있다. V11 runner는 실제 현재 모듈을 읽도록 import 경계만 맞추고, 실제 반환된 matched-feature/condition 자료를 판정하도록 갱신해야 한다. 이때 출력 기대와 성공 규칙은 바꾸지 않는다.

pure 결과에 경고 근거가 있다는 것은 UI에 경고가 보인다는 뜻은 아니다. C5 표면 기준은 추천 컴포넌트의 실제 렌더/브라우저에서 읽히는지 별도 관찰해야 한다. 함수 평가·서버 API·클라이언트 표시·소유 도구함 상태를 하나의 성공 수로 합치지 않는다. 새 점수 판단 역시 기존 6.2.4 원문과 평가 수행 증거를 따로 검토하며, 개선된 20개 결과만으로 전반적인 추천 정확성·사용자 만족도·전체 목표 완료를 선언하지 않는다.
