# V11 검색 정밀도: 일반 규칙 제안

확인일 2026-09-12. 현재 `site/lib/catalog-search.ts`, 실제 카탈로그의 feature/useCase, 검색 테스트를 다시 읽었다. 소스·운영·브라우저를 변경하지 않았으며 이 파일만 작성했다. 부정 구문과 조건 미확인 안내는 root가 구현하는 범위로 두고, 여기서는 긍정 업무의 정밀도와 근거 구분에 한정한다.

## 권장되는 작은 변경

**핵심 대상과 행동을 분리하고, 같은 기능 또는 같은 용례에서 둘이 함께 맞는 경우를 직접 근거로 삼는다. 한쪽만 맞는 기능은 부분 관련으로 구분한다.** 현재 제품 순위에 예외를 추가하지 않고도 ‘프롬프트 작성→보고서 작성’, ‘이미지 입력→이미지 생성’의 잘못된 연결을 줄일 수 있다.

현재 `concepts`의 한 배열 안에는 대상과 행동이 섞여 있다. 예를 들어 문서/보고서와 작성/다듬이 모두 같은 그룹이어서, 기능 설명에 `작성`만 있어도 글쓰기 개념 전체를 매칭한다. `score(f.description)`의 가중치를 전체적으로 낮추기보다 **그 행동이 무엇을 대상으로 하는지 확인한 뒤 근거 등급을 정하는 것**이 핵심이다.

## 1. 대상·행동·조건을 서로 확장하지 않기

| 역할 | 예시 | 허용 범위 |
|---|---|---|
| 핵심 대상 | 문서/글/보고서/제안서, 이미지/그림/일러스트, 코드, 프로토타입/화면 흐름, 상태/마감일/캘린더, 폼/앱 간 데이터 | 같은 역할의 업무 표현을 연결. 단순 ‘텍스트’는 프롬프트 입력에도 쓰이므로 무조건 문서 작성 대상으로 확장하지 않음 |
| 행동 | 작성/초안/생성/제작, 수정/다듬기, 분석/읽기, 검색/조사, 요약, 입력/업로드, 출력, 전달/연결, 저장/배포 | 행동끼리도 방향을 보존. 입력·분석을 생성과 동일시하지 않고, 검색·요약·출처 인용도 각각 구분 |
| 조건·환경 | 무료, 한국어, 앱/API, 플랜·한도 | 별도 제약/미확인 판단. 긍정 기능 가점을 만드는 단어로 쓰지 않음 |
| 일반 표현 | 필요, 업무, 도구, 사용, 만들고 싶어요, 해주세요 | 그 표현 하나로 특정 분야/기능을 활성화하지 않음 |

`작성/생성/제작/만들기`는 여러 분야에서 쓰인다. **행동만으로 문서·디자인·자동화 분야를 추론하지 않는다.** `초안`, `퇴고`, `리팩터링`, `프로토타입`처럼 업무 의미를 이미 포함한 단어는 복합 개념으로 인식할 수 있다. 이때도 `초안→특정 제품`이 아니라 초안/문서 작성이라는 실제 용례·기능과 연결한다.

짧은 입력 `코딩`, `회의`, `자동화`에는 명시적인 대상+행동 두 단어를 강제하지 않는다. 이미 업무를 나타내는 단일 개념이나 핵심 명사만 있는 질의는 그 의미 범위에서 검색하되, 제공되지 않은 세부 행동까지 충족한다고 설명하지 않는다. “회의”를 찾았다고 자동 녹음·녹취·회의록을 모두 제공한다고 추론하지 않는다.

## 2. 같은 근거 단위에서 의미를 연결하기

가장 작은 근거 단위는 **feature 하나의 name+description** 또는 **useCase 문자열 하나**다. 제품의 다른 기능을 합쳐 새로운 기능 관계를 만들지 않는다.

- `이미지 생성`: 이름/설명에 이미지와 생성의 관계가 직접 나타난 feature는 직접 근거다. `텍스트·이미지 입력` 및 ‘텍스트를 출력’은 이미지 대상만 맞으므로 부분 관련이다. 이미지 기능과 별도의 파일 생성 기능을 합쳐 이미지 생성을 지원한다고 하지 않는다.
- `보고서 작성`: `글 작성·수정` 또는 `문서 초안`은 직접 근거가 될 수 있다. ‘프롬프트를 작성해 이미지를 생성’은 행동 `작성`만 겹치고 대상이 달라 직접 근거가 아니다.
- `앱 간 데이터 전달`: 같은 용례의 ‘앱 간 데이터 이동’이나 한 feature의 트리거→연결 앱 작업은 직접 근거가 될 수 있다. 설명 어딘가의 ‘플랫폼’과 별도 ‘자료 제작’을 합쳐 자동화 기능으로 해석하지 않는다.
- `마감일을 캘린더로 보기`: 관련된 상태/날짜/캘린더 기능 두 개를 각각 보여줄 수는 있다. 다만 특정 연동·자동화 동작이 요청됐다면 따로 흩어진 명사만으로 그 동작까지 가능하다고 설명하지 않는다.

기능 **제목의 구체 구문**을 먼저 본다. description은 제목의 의미를 뒷받침하거나 같은 문장·가까운 구문에서 대상/행동을 연결하는 데 쓴다. 작은 주변 범위를 활용할 수 있지만 무조건 ‘몇 글자 안에 두 단어가 있음’만으로 충분하다고 보지는 않는다. `이미지를 입력하고 텍스트를 생성`은 가까운 위치에 이미지/생성이 있어도 방향이 다르기 때문이다. 완벽한 문법 분석을 추가할 필요는 없으며, 명확한 직접 구문을 우선하고 불명확한 연결은 부분 관련으로 남기는 것이 작고 보수적이다.

## 3. 직접 일치·부분 관련·이름 일치의 출력 경계

| 근거 등급 | 예시 | 추천에서 가능한 설명 |
|---|---|---|
| 직접 기능 | 요청 대상+행동을 같은 feature에서 확인 | 해당 feature를 실제 조건·상태·공식 URL과 표시 |
| 직접 용례 | `문서 초안`, `앱 간 데이터 이동` 등 실제 useCase에 요청 업무가 존재 | “등록된 활용 예시와 연결” 표시. 관계없는 feature를 그 용례의 근거로 대체하지 않음 |
| 부분 관련 | 이미지 입력만 일치, 문서 분석만 일치, 일반 업무 분야만 연결 | “일부 관련 정보”로 구분하고 요청 행동을 직접 확인하지 못했음을 표시. 지원으로 승격하지 않음 |
| 제품명/별칭 | 정확한 이름·등록 별칭 | 이름 검색 결과로 유지. 억지로 matched feature를 만들지 않음 |

직접 feature만 필수로 만들면 현재 ChatGPT의 `문서 초안`처럼 **용례에는 있지만 별도 feature 행에는 없는 근거**가 사라진다. 반대로 이 후보를 남기려고 이미지 생성 feature를 문서 작성 근거로 붙여서는 안 된다. 원본 용례를 별도의 근거로 쓰면 두 문제를 함께 피할 수 있다.

최소 반환 변경은 기존 `Tool + relevance` 배열과 `matchedUseCases`를 유지하면서 `matchedFeatures`를 직접 근거에 한정하고, 필요하면 별도 `relatedFeatures` 또는 근거별 match 수준을 추가하는 것이다. 기존 feature의 name/description/status/condition/sourceUrl 자체는 그대로 보존한다. UI가 이미 표시 중인 ‘조건부 지원/확인 필요’는 **제품 기능의 공식 상태**이고, 직접/부분 관련은 **현재 질의와의 관계**이므로 서로 바꿔 쓰지 않는다.

다중 업무에서는 모든 단어를 AND로 요구해 0건으로 만들 필요는 없다. 매칭된 업무와 직접 근거만 설명하고 나머지 요청은 확인되지 않았다고 남긴다. 기능 여러 개의 부분 점수를 더해 모든 요구가 충족된 것처럼 만들지 않는다. 직접 근거가 없는 결과도 필요할 수 있으나, 직접 근거가 있는 후보와 같은 설명으로 상위 여섯 개를 채울 필요는 없다.

## 4. 순위와 토큰의 일반 불변량

- **점수의 양보다 근거 등급을 먼저 구분한다.** 같은 질의에서 직접 대상+행동 근거는 행동 단어만 여러 번 겹친 후보보다 앞에 온다. 제품명 정확 일치는 기존 범위 필터 안에서 보존한다. 부분 관련 결과의 최대 누적 점수가 직접 근거를 역전하지 않도록 중복·상한을 둔다.
- 동일 개념 반복과 긴 설명은 추가 관련성을 만들지 않는다. 질의의 동의어 중복·한 feature 내부의 반복은 한 번만 세고, 유사한 feature 행을 많이 가진 제품이 자동으로 승리하지 않게 한다. 현재 IDF는 등급 안에서 동점을 세분하는 수단으로 유지할 수 있다.
- 제목·용례·본문의 가점은 근거 판정과 같은 매칭 결과를 재사용한다. rank에서는 직접이라며 올렸지만 renderer에서는 부분 관련 feature만 내보내는 불일치를 피한다.
- 내부 정렬을 등급/세부 점수의 튜플로 바꾼다면 외부 `relevance`도 그 순서를 보존해야 한다. `/api/search`는 결과를 숫자 score로 다시 정렬하므로, 배열만 등급순으로 정렬하고 relevance를 옛 값으로 남기면 Explore/Recommend와 API의 도구 순서가 달라질 수 있다. 내부 점수를 사용자 적합 확률·품질 점수로 표시하지 않는다.
- 영문 일반 업무 토큰은 전체 단어 또는 명시적인 어근/변형을 사용한다. `art→Artifacts` 같은 임의 부분 문자열을 직접 업무 근거로 쓰지 않는다. 제품명 접두 검색을 유지한다면 name/alias 필드에서만 별도의 약한 탐색으로 구분한다.
- 한국어는 핵심 명사에 붙은 허용 조사·어미를 처리하되 다른 명사의 중간을 자르지 않는다. `글/폼/표`처럼 실제 업무 대상인 한 글자는 확인된 사전 안에서 허용할 수 있다. 모든 한 글자를 허용하거나 단순 길이≥2 규칙만 쓰는 두 극단을 피한다. ‘폼’과 ‘플랫폼’은 같은 명사가 아니다.

## 5. 구현 구조를 따라 쓰지 않는 최소 관계 테스트

합성 도구의 ID·이름을 무작위로 바꾸거나 입력 배열 순서를 바꿔도 아래 관계가 유지돼야 한다. 이 테스트는 특정 실제 제품을 고정 순위에 놓지 않는다.

1. `이미지 생성` 질의에서 feature `이미지 생성`은 `이미지 입력/텍스트 출력`보다 직접 근거가 강하다. 별도 `파일 생성` 행을 추가해도 이미지 입력 후보가 직접 이미지 생성으로 승격되지 않는다.
2. `보고서 작성`에서 `글 작성·수정`은 `프롬프트를 작성해 이미지를 생성`보다 직접 근거가 강하다. 후자 설명의 `작성` 반복 횟수를 늘려도 관계가 뒤집히지 않는다.
3. `문서 초안` useCase만 가진 후보는 직접 용례 근거로 남고, matchedFeatures에 임의 이미지/검색 기능이 붙지 않는다.
4. `이미지를 분석`과 `이미지를 생성`은 같은 결과를 무조건 같은 순서로 반환하지 않는다. 입력과 생성의 방향을 바꾸면 해당 근거 등급도 달라져야 한다.
5. `코딩`처럼 단일 업무 질의와 `프로토타입` 같은 복합 명사는 검색 가능하다. 모든 입력에 대상+행동 두 토큰이 있어야 한다는 회귀를 만들지 않는다.
6. 영어 `art`가 `Artifacts`의 직접 기능 일치로 표시되지 않는다. 실제 전체 기능명 `Artifacts`와 등록 제품명/별칭 검색은 보존한다.
7. 설명에 무관한 문장·동의어를 덧붙여도 직접 근거의 우선순위가 변하지 않는다. 모든 근거는 원 feature/useCase에 존재하며 원문 조건/URL을 바꾸지 않는다.
8. 같은 새 matcher를 거친 필터 결과는 category/kind/free/korean/owned 제약의 교집합이다. 기존 빈 질의/unknown 질의 및 API 배열 계약은 그대로다.

실제 카탈로그에서는 위 일반 규칙을 적용한 뒤 고정20·보류16과 기존 API 테스트를 같은 기대대로 다시 실행한다. 이 보고서는 새 알고리즘을 실행한 결과나 개선 성공률을 주장하지 않는다. 불가피한 0건·부분 관련 후보를 숨겨 성공 수를 올리지 않으며, 특정 사례를 맞추기 위해 제품 ID·완성 질의·새 공식 기능 사실을 규칙에 추가하지 않는다.
