## 4. 7.2.4 실제 읽기 과업

현재 근거: `site/tests/api.test.mjs:16`은 alpha 계정 삭제 뒤 beta의 답글 본문 보존을 DB에서 검사한다. `Community.tsx:16`은 부모 GET와 published 답글 GET를 별도로 요청하고, 부모가 없으면 ‘삭제되었거나 공개되지 않은 글입니다.’를 표시한 뒤 답글 목록을 계속 렌더한다. `api/community/route.ts`는 published 부모만 반환하고 답글은 parent_id로 따로 조회한다. **이 소스 사실은 UI 읽기 완료 증거가 아니다.**

| 순서 | root가 준비/관찰할 상태 | 충분한 실제 증거 |
|---|---|---|
| C01 사전 고정 | 부모 P 작성자A, 답글 R 작성자B(user_id 다름), 각 실제 id/상태/짧은 고유 문구 기록 | 로컬 fixture여도 실제 앱의 저장 형태/관계를 유지하고 QA임을 명시. A와 B가 실제 사람 두 명이라고 주장하지 않음 |
| C02 기준 읽기 | `/community/P`에서 부모와 B 답글이 정상 보임 | URL·role·D/M 또는 수행한 실제 viewport, parent/reply 문구·작성자 구분 |
| C03 목표 읽기 | 삭제 또는 숨김 상태인 **같은 P의 상세 URL** 다시 방문·전체 reload | 부모 본문/평점이 보이지 않고 비공개/삭제 안내가 이해됨; B 답글의 전체 본문·작성자·날짜를 실제 읽을 수 있음; 무한 로딩/오류/빈 목록으로 바뀌지 않음 |
| C04 탐색 마무리 | 남은 답글까지 스크롤하고 ‘목록으로’ 복귀 | 답글을 찾고 읽는 과업이 완료됐다는 관찰. DOM의 보존 숫자만 제시하지 않음 |
| C05 보완(권장) | 같은 공유 UI 분기에서 나머지 삭제/숨김 상태도 확인; 숨김은 복원 후 비교 가능 | 고정 문구는 단수 `A deleted/hidden parent`이므로 두 상태를 무조건 별도 추가 게이트로 만들지 않는다. 어느 상태를 실제 봤는지 명시하고 다른 상태는 DB/소스 근거인지 구분 |

원문을 그대로 판정하면 적어도 한 삭제/숨김 부모와 **다른 작성자의 실제로 보이는 답글**을 읽는 완료 과업이 핵심이다. V10 84/85는 정상 부모/답글이므로 대체하지 못한다. 현재 코드에서 부모가 없으면 `답글 N` 제목과 ‘답글 작성’ 버튼은 함께 사라지고 답글 행은 남는다. 남은 행을 답글로 알아볼 수 있는지 실제 확인할 우선 지점이다. 새 답글 작성/수정 성공까지를 이 읽기 게이트의 추가 조건으로 만들 필요는 없다.

## 5. 8.5.4 운영 전체 내보내기·다운로드·삭제 과업

현재 UI: `Preferences.tsx`의 ‘내 기록 내보내기’는 `/api/export` download 링크, ‘내 데이터 삭제’는 inline 확인을 열고 정확히 **내 기록 삭제**를 입력해야 ‘모든 내 기록 삭제’를 활성화한다. API는 `api/workspace/route.ts:41–51`에서 개인 기록/이메일/알림/피드백을 지우고 소유 게시물·평점을 익명화/삭제 상태로 바꾼다. 다른 작성자 답글은 지우지 않는다. 실제 export 구조는 `api/export/route.ts:7–17`의 records/posts/notifications/notificationCards/feedback/emailDeliveries/emailOutbox/emailSchedule다.

| 순서 | 운영 UI 과업 | 기록할 충분한 증거 / 완료가 아닌 경우 |
|---|---|---|
| E01 상태 확인 | 소유자 전용 **실제 배포**에서 현재 계정과 삭제 대상 범위를 확인하고 고유 식별 가능한 QA/개인 기록 목록 기록 | 공개 접근 범위를 바꾸지 않는다. 비어 있는 계정을 지우고 모든 종류의 실데이터 삭제를 검증했다고 하지 않음. 실제 다른 사용자 기록을 QA로 취급하지 않음 |
| E02 UI 내보내기 | 실제 ‘내 기록 내보내기’를 클릭하고 브라우저 다운로드가 완료된 파일을 확보 | 클릭만/HTTP200만/로컬 export API 테스트만은 download 완료가 아님. CUA가 다운로드 산출물을 노출하지 못하면 해당 단계 미관찰을 명시 |
| E03 파일 확인 | 받은 실제 JSON 파일을 열어 parse하고 exportedAt·파일명/바이트/hash·본인 데이터의 알려진 항목 확인 | records의 저장 필드/조건 이력, 존재하는 소유 글·알림 버전/개인 카드·feedback·email 이력의 연결을 실제 보유 데이터와 대조. 빈 배열은 빈 상태 검증이며 가짜 접수번호/평가를 만들어 채울 필요 없음. 다른 소유자 자료·비밀키가 없는지 확인 |

안전하게 준비할 수 있는 읽기·파일 확인·로컬 사전 검증을 먼저 끝내야 한다. 운영에 삭제할 수 있는 대상이 없거나 실제 파일 회수가 막히면 **8.5.4는 미완료로 남기고 구체 단계만 보고**한다. ‘로컬에서는 되니 운영도 완료’로 바꾸지 않는다. 원래 8.5.1–8.5.3은 이미 PASS이며, 이 추가 UI 관찰은 그 점수를 다시 더하는 작업이 아니다.

## 6. 증거 행 형식과 최종 판정 준비물

각 행은 `gate / inventory ID / source·deployment / local or production / exact URL / role·QA provenance / timestamp / 실제 CSS viewport·zoom / action-before-after / screenshot 원본 path / DOM 보조값 / 실제 읽은 부분 / 미관찰·오류 / 수정 후 재관찰`을 포함한다. 파일 확장자가 png여도 실제 JPEG bytes면 원본 형식을 그대로 기록한다. screenshot pixel 크기와 CSS viewport가 다르면 둘 다 기록한다.

3.4.4는 V01–V09의 판독 가능한 D/M 구간과 V10 교차 비평표, 7.2.4는 C01–C04의 실제 목표 읽기, 8.5.4는 실제 운영 E01–E07의 다운로드 파일·삭제 전후 UI를 묶어 판단할 수 있다. 어느 하나의 부분 관찰도 다른 게이트나 모든152개 기준으로 확대하지 않는다. 이번 문서는 세 게이트의 UNVERIFIED/weight/earned와 기존 28개 principal 정의를 모두 보존한다.
