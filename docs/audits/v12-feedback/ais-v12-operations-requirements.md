**최소 입증:**

### P0 — 동의한 실제 이메일 전달의 입증과 추적

**관찰:** [이메일 코드:40](/Users/bigmac_moon/dev/ai_score/site/lib/notifications.ts:40)는 `RESEND_API_KEY`, `EMAIL_FROM`, `SITE_URL`을 확인한 뒤 Resend에 실제 POST하는 함수다. 대기열, 사용자·소식 키의 중복 방지, 발송 건의 idempotency key, 재시도 상한, 오래된 불확실 재시도의 수동 검토 전환, 발송 직전 동의·자격·현행 소식 재확인이 구현돼 있다. `/api/workspace`는 이메일 주소를 로그인 계정 주소로 지정한다. 따라서 “이메일 기능 코드가 없다”는 평가는 부정확하다.

**미입증·추적 갭:** 고정 V11에는 실제 연결과 제공사 영수증이 없다. `/api/capabilities`는 세 환경 변수의 존재만 판단하며 발신자 인증이나 전달 성공까지 확인하지 않는다. 전송 응답의 `id`는 존재를 검사하지만 저장하지 않는다. DB의 `sent`는 코드상 제공사 성공 응답을 받은 상태이며 수신함 도착이나 읽음을 뜻하지 않는다. `email_outbox`에는 제공사 메시지 ID·전달 상태 연결 필드가 없고, 확인한 API 목록에 전달/반송 결과 수신 경로도 없다. 제공사 영수증을 외부 운영 기록으로 연결하는 방법도 가능하므로 특정 웹훅 구현만을 필수로 강제하지 않는다.

**최소 입증:**

1. 실제 발신자 설정과 전송 서비스가 준비된 환경에서, 명시적으로 동의한 통제된 수신 계정으로 한 건을 발송한다. 사용자 동의 기록 → 앱 알림 ID·소식 버전 → 대기열 건 → 제공사 메시지 ID·시각·상태 → 수신 확인을 연결한다. 민감한 비밀값을 보고서에 노출할 필요는 없다. 이 검토에서는 발송하지 않았다.
2. “제공사 접수”와 “수신 확인”을 기록상 구분한다. 실제 수신을 확인하지 못했으면 그렇게 남기고 완료 표현을 제한한다. 앱 알림함 표시와 mock 응답은 실제 전달 영수증을 대신할 수 없다.
3. 동의 철회·행사 만료·자격 미확인·관심 변경 후 발송/재시도 제외, 동일 건 재시도 중복 방지, 이메일 실패 후 앱 기록 보존을 확인한다. 현재 설정 저장 시 대기열을 즉시 취소하지는 않으며 **다음 발송 처리 때 재확인하여 취소**한다. 설계의 “수신 해제 시 대기 발송 취소”를 충족했다고 설명하려면 이 차이를 정리하고 저장→대기열→작업 재개 흐름을 입증해야 한다.

실제 비밀값이 지금 미설정이라고 단정하지 않는다. 코드 기반과 실제 운영 증거를 별개로 기록해야 한다.

### P1 — 공개 정보와 개인 알림의 운영 담당·주기·검수 종료 기록

**관찰:** 소스 갱신은 ETag·본문 변화·이전 성공 시각·오류·검토 필요 상태와 `sync_runs`를 저장한다. 일반 페이지 변경을 사실로 자동 확정하지 않는 점은 설계와 맞는다. [관리 API:5](/Users/bigmac_moon/dev/ai_score/site/app/api/admin/route.ts:5)는 신고·기능 제안, 최근 동기화 10회, 이메일 상태별 개수를 제공한다. 관리 행동은 게시물 숨김/복원과 신고 해결이다. 공개 콘텐츠의 책임자·다음 검수 시점·밀린 검수·검수 결과 반영을 관리하는 주기는 이 코드와 README에서 확인되지 않았다.

**중요한 연결 차이:** `currentNotices()`는 `source_snapshots`의 새 피드가 아니라 정적 카탈로그의 `latestUpdate`와 `promotions.json`을 사용한다. 따라서 소스 확인을 정기화하기만 해서는 새 피드 소식이 개인 알림에 연결되거나 새 행사가 검수·발행되지 않는다. 수동 검수 후 발행하는 과정은 허용되지만, 누가 언제 변경을 확인하고 공개 데이터·소식·행사를 갱신하는지 운영 경로가 필요하다. RSS 수집 성공을 기능 사실의 검수 완료로도 보지 않아야 한다.

**최소 입증:**

- 지속 가능한 공개 주제·도구 범위, 발행/갱신/검수 담당, 검수 시간 또는 주기, 변경·오류 접수 후 처리 책임, 다음 확인 시점을 명시한다. 개인 비용·해지·알림 운영도 함께 넣는다. 이 보고서에서 임의로 담당자나 SLA를 배정하지 않는다.
- 최소 한 운영 주기에 대해 출처 변경/오류 발견 → 담당 확인 → 사실 검수 또는 보류 → 공개 정보·행사·알림 후보에 반영 → 처리 결과·다음 확인 기록을 남긴다. 검토할 것이 없었다면 확인 범위와 무변경 결과를 남긴다.
- 운영자가 실패한 정기 실행, 오래된 출처, 미완료 검수, 실패/검토 필요 이메일, 고객 피드백을 발견하고 처리한 기록을 확인한다. 자동화 대시보드만이 유일한 방법은 아니며 초기에는 실제로 사용하는 담당·주기 문서와 처리대장으로도 운영 경로를 입증할 수 있다. 단, v0.6의 도움 지표는 대시보드 요구가 별도로 있다.

알림 설계의 중요 변경 버전과 정정 전달도 운영 확인이 필요하다. 현재 프로모션 키는 `promotion:<id>:<checkedAt>`이고 업데이트 키는 발표일 또는 확인일이다. 단순 재확인 날짜 변경과 가격·자격의 의미 있는 변경을 분리하는 명시적 버전·정정 흐름은 확인되지 않았다. 이는 동일 행사 재확인으로 새 알림을 만드는지, 잘못 전달한 카드가 정정 상태로 이어지는지 고정 사례로 검증할 지점이다. 현재 동작을 실행 관찰한 결과라고 주장하지 않는다.

### P1 — 두 축의 도움 피드백과 비회원 경로·분모

**관찰:** 커뮤니티의 도움이 됐어요 반응, 신고·기능 제안, 개인 보관 항목의 이유·결과·메모는 있다. 그러나 [커뮤니티 반응 API:4](/Users/bigmac_moon/dev/ai_score/site/app/api/community/actions/route.ts:4)는 로그인 사용자만 허용하고 글 하나에 대한 토글 반응을 저장한다. 이를 정보 획득·이해 응답과 개인 활용·관리 응답으로 나누거나 비회원 정보 응답으로 사용할 수 없다. 현재 Admin 집계에는 해당 두 지표, 질문·분모·수집 기간이 없다. “피드백이 전혀 없다”가 아니라 **요구한 운영 피드백 구조가 없다**는 판단이다.

**갭:** 정보/개인 관리 축과 맥락을 구분하는 선택형 응답, 비회원의 정보 응답 경로, 반복 처리 기준, 수집 기간·질문 버전·분모 정의와 별도 대시보드 표시가 필요하다. 알림에는 구체적으로 도움이 된 이유, 조건이 안 맞음·중복·불필요함·해제 이유를 운영 개선으로 연결할 수 있어야 한다. 매 기사마다 강제 설문을 붙이는 것은 요구가 아니다.

**최소 입증:**

1. 비회원 정보 이용과 로그인 개인 관리 이용을 각각 수행하여 서로 다른 축에 응답이 기록되고 대시보드에 분리되어 보이는지 확인한다. 테스트 데이터는 QA로 표시하며 실제 사용자에게 도움이 됐다는 증거로 소개하지 않는다.
2. 같은 방문의 반복 응답·새 방문·계정 응답의 처리 규칙을 정한다. 익명 방문 키는 정확한 고유 인원 수가 아니다. 응답 수만 확보했다면 그 분모를 응답으로 표시하고 전체 이용자의 도움 비율로 확대하지 않는다.
3. 지표마다 질문, 집계 기간, 응답 분모와 사용·재사용 분모를 명시한다. 미시도·미응답·관찰 기간 미완료를 구분할 수 있는 집계 설계와 해당 데이터가 없다는 상태를 제공한다. 미응답률 등을 제시하려면 설문 노출/응답 대상 분모도 필요하다.
4. 두 수치를 합산한 임의의 종합 점수로 대체하지 않고, 자기보고를 학습·업무 성과의 확정값으로 표현하지 않는다. 피드백 확인 담당·검토 주기·결정/보류 이유를 운영 기록과 연결한다. 코드와 샘플 집계는 수집 가능성을 입증하지만, 실제 고객 효과를 입증하는 것은 아니다.

## 이번 요구로 확대하지 않을 범위

전 시장 실시간 탐지, 모든 정보를 자동으로 사실 확정하기, 이메일 이외의 외부 채널, 자동 구독 해지, 실제 구매/해지로 효용을 입증하기는 이번 운영 최소 요건이 아니다. 선택한 행사 마감 재알림과 결제 기한 알림 확장은 [설계:110](/Users/bigmac_moon/dev/ai_score/docs/superpowers/specs/2026-09-11-cancellation-promotion-alerts-design.md:110)의 후속 기능이다. 현재 결제 예정 알림이 `emailAllowed:false`인 점만으로 첫 출시 이메일 요구 전체를 새로 확장하지 않는다.

본 보고서는 요구·소스의 대조이며 배포 운영 테스트나 실제 사용자 연구가 아니다. 운영 설정 미열람, 실제 발송 미수행, 무방문 실행 미관찰을 완료 증거로 바꾸지 않았다.
