## 5.1.4: 기존 매트릭스의 Z 칸을 실제로 채우기

[기존 V10 matrix](/Users/bigmac_moon/dev/ai_score/docs/audits/2026-09-12-v10-screen-matrix.md:16)는 **D/M/Z**, Z=실제 브라우저 200%, 각 주 화면을 명시한다. [V16 inventory](/Users/bigmac_moon/dev/ai_score/docs/audits/v16-ui-recovery/ais-v16-ui-gate-inventory.md:21)가 이미 같은 28 principal과 S01–S12 확장을 다시 연결했다. 이를 더 작은 대표 홈 한 장으로 줄이면 ‘complete’에 맞지 않는다. 반대로 새 route×기기×폭×모든 데이터 값의 대규모 조합표를 만들 필요도 없다.

- **기존 28행 그대로**: P01–P20 공개 20개 + A01 실제 관리자 + M01–M07 개인 7개에 현재 Z 관찰을 연결한다. `/news` 3탭과 `/my` 7메뉴는 이미 독립 행이고, 20제품/4가이드 각각을 새로운 principal로 늘리지 않는다. 같은 상세 템플릿의 구조가 같은 변형은 묶되 실제 URL과 본 상태를 밝힌다.
- **기존 추가 상태 그대로**: G01 비로그인 마이, A02 권한 없음, E01 404, E02 공통 오류 및 S01–S12의 현재 중요한 확장은 해당 기존 행 아래에 남긴다. 가능하지 않은 상태는 미관찰 이유를 기록한다. 기존 인벤토리의 본문/폼/표 완전성 칸이 비었는데 principal 상단만 보고 전체 완료로 선언하지 않는다. 모든 내용 조합을 새 fixture로 생성하라는 뜻은 아니다.
- **확대의 실재 확인**: Native Chrome의 실제 zoom 표시 200%를 남기고, 같은 창에서 페이지 `innerWidth/innerHeight`, document clientWidth/scrollWidth를 별도로 기록한다. 좁게 만든 창·CSS zoom/transform·이미지 축소·OS 화면 확대는 브라우저 200%와 구분한다. 확대 전후 실제 CSS 폭이 바뀌므로 200% 상태를 기존 1440/390 CSS viewport라고 자동 기입하지 않는다.
- **한 번의 확대 통과에서 필요한 범위**: 각 행의 상·중·하 본문, 마지막 CTA/footer, 긴 이름/조건/숫자, 초점 표시를 본다. 표는 문서 폭과 해당 scroller 폭을 분리하고 양끝 열에 도달한다. 모달은 제목/닫기부터 긴 본문·하단 저장/취소까지 도달하며 키보드로 조작할 수 있는지 확인한다. 일부 가로 표 스크롤 자체를 실패로 보지 않고, 행/열과 조작이 접근 가능한지 읽는다.
- **확장은 기존 몸체 단위로 재사용**: V17의 V01–V07은 이미 S06–S10의 긴 폼·결과·보고서를 분해한 것이므로 같은 진입 경로와 QA를 재사용해 Z만 채운다. 공통 Modal의 기본 초점 순환은 공통 근거를 참조할 수 있지만 서로 다른 폼 하단이나 서로 다른 표의 오른쪽 열은 하나로 대체하지 않는다. 메뉴/dock/toast는 한 공통 관찰로 연결하며, 화면마다 같은 제어를 반복할 필요는 없다.
- 기존 matrix의 760/761,1050/1051,500px 설명목록 전환은 **레이아웃 가족별** 증거를 재사용하거나 부족한 전환만 확인한다. 모든 28행에 모든 분기점·D/M별200% 조합을 새로 강제하지 않는다. 320px 추가 관찰은 원문에서 선택 보완이며 native200%를 대신하지 않는다.

완료 기록은 기존 ID에 `정확 URL·query / 현재 source·환경·role·QA 상태 / Chrome 실제 zoom / CSS viewport / raster 크기 / 문서와 내부 영역 폭 / 판독한 상중하·양끝 / 결과·수정 재확인`을 붙이면 된다. V17 JPG의 D1425×891/M375×812 비례 축소는 보이는 내용을 읽는 증거지만 native zoom 숫자가 아니다. 관찰되지 않은 칸이나 발견한 실제 차단 결함은 그대로 남긴다.

## 5.2.4: 소수의 연결 과업으로 세 요소를 모두 실제 관찰

이 원문은 **읽기 순서·설명·상태 알림의 observed run**을 요구하며, 28페이지 전체 VoiceOver sweep을 별도로 요구하지 않는다. 이미 [V7 독립 검토](/Users/bigmac_moon/dev/ai_score/docs/audits/2026-09-12-v7-accessibility-review.md:96)는 주/개인 메뉴 상태, 비교 표 관계, 반복 동작 이름, 한 결과 알림의 실제 관찰을 권고했다. 다음 세 연결 구간이면 현재 사이트의 주요 읽기 구조를 한정해서 검증할 수 있다.

| 연결 구간 | 실제로 읽고 조작할 것 | 세 요소의 증거 |
|---|---|---|
| 공개 Shell → `/explore` 결과/0건 | VoiceOver로 주 메뉴/현재 페이지·본문 이동·h1·검색·분야/종류/체크박스를 따라가고, 검색어나 필터를 바꿔 결과 수/0건 안내를 확인한다. 0건은 기존 동작으로 만들고 조건 초기화로 돌아온다. | 합리적인 읽기 순서, 컨트롤 이름/현재 값/체크 상태, `role=status` 결과 변경이 실제로 전달되는지. 숫자가 DOM에 있다는 사실과 읽힌 결과는 구분한다. |
| `/compare?ids=chatgpt,claude,notion`의 실제 3열 표 | 도구 열 이름과 기능/조건 행을 오가며 현재 읽는 값이 어느 제품·항목인지 알 수 있는지 확인한다. 원문/조건 설명과 반복 저장·비교 동작의 대상 이름을 읽는다. | 표의 행/열 문맥, 설명·조건 문구가 실제 읽히는지, 반복 버튼을 구분할 수 있는지. 모든 제품을 반복하거나 표 존재만으로 통과할 필요는 없다. |
| `/my?tab=subscription` → 기존 `조건 이력` 또는 신규 구독 모달 | 개인 메뉴의 현재 선택을 읽고, 제목·초기 초점·필드 이름/도움말·현재 값·확장 상태를 따라간다. 현 QA의 같은 적용일 미리보기 같은 **저장 없는 기존 오류 경로**를 사용하면 alert 전달을 확인할 수 있고, 정상 경로/닫기로 돌아온다. | 긴 폼의 순서·금액/미확인 설명, 오류 상태가 생겼을 때 실제 알림, 닫기 후 원 제어를 다시 찾는지. 공개 게시·실제 결제 저장·철회·삭제는 필요 없다. |

세 번째 구간의 오류까지 성공해야 첫 번째 결과 알림을 인정한다는 새 게이트를 만드는 것은 아니다. 결과 status와 alert 중 실제 수행한 변화/범위를 적고, **관찰된 중요한 상태가 전달되지 않는다면 그 결함을 숨기지 않는다**. 반대로 시간상 하나의 상태 변화만 확인했다면 모든 알림 경로를 검증했다고 확대하지 않는다. 설명은 label 존재 여부만 보지 말고 금액 조건/미확인/보조 안내를 reader로 실제 읽을 수 있는지 확인한다.

현재 소스의 출발점은 `Shell.tsx`의 주 메뉴·aria-current·skip, `Explore.tsx`의 결과 status, `Provider.tsx`의 공통 polite toast, `Modal.tsx`의 labelled dialog, `TermsEditor.tsx`의 충돌 alert다. 이것들은 **관찰 후보와 이미 구현된 전제**이고 실제 읽기 성공은 아니다. 로그에 `VoiceOver+Chrome / 환경·버전 / URL·role / 수행한 순서 / 실제 들리거나 reader 출력으로 확인한 문구 / 예상과 다른 발화·누락 / 수정 후 재실행`을 남긴다. OS에서 VoiceOver를 켠 화면, DOM accessibility tree, aria-* 속성만으로 observed run을 대신하지 않는다.
