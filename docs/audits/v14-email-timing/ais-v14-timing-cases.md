## 1. 저장·계산 단위

- 사용자 설정은 이메일 동의, `daily` 또는 `condition`, IANA 시간대, 정확한 `HH:mm`을 갖는다. 예: `Asia/Seoul`, `09:00`. 브라우저 추정값은 제안할 수 있지만 수신 동의와 확인된 저장값을 대신하지 않는다. 서버·사용자 기기의 기본 시간대를 계산에 사용하지 않는다.
- HH:mm은 00:00–23:59의 5자리만 허용한다. `9:00`, `24:00`, `09:60`, 초를 붙인 값은 거절한다. 잘못된 시간대를 UTC나 서울로 묵시적으로 바꾸지 않는다. 이름이 유효한지는 실제 배포 런타임의 Intl로 확인한다. UTC는 허용하며 이 제품은 `+09:00` 같은 고정 오프셋 입력 대신 명명된 시간대를 받는다.
- 절대 시점은 UTC instant, 사용자 일자는 해당 시간대에서의 Gregorian `YYYY-MM-DD`, 수신 시각은 벽시계 HH:mm으로 구분한다. `toISOString().slice(0,10)`을 사용자 현지 날짜로 쓰지 않는다.
- 각 발송/요약 슬롯은 사용자, 채널, **예정 현지 날짜·그때의 시간대/시각**, UTC 예정 시점, 상태를 기록한다. 이미 평가하거나 전달한 슬롯은 설정 저장으로 삭제·초기화하지 않는다. 정책 버전은 추적 정보이며 같은 소식의 재전송 키가 아니다.
- 상한은 소식 개수가 아닌 **실제 이메일 한 통(envelope)** 기준이다. 요약 한 통에 5개 행사가 들어 있어도 한 통이다. 발송 중/결과 불확실한 예약은 성공 여부를 확인할 때까지 자리를 점유한다. 동시 작업 두 개가 각각 마지막 한 자리를 쓰지 않도록 확인·예약을 원자적으로 처리해야 한다.

## 2. 현지 날짜와 DST를 UTC 예정 시점으로 바꾸는 규칙

특정 날짜 D의 HH:mm을 시간대 Z에서 해석한 **한 개의 canonical due instant**를 사용한다.

1. 해당 벽시계 시각이 한 번 존재하면 그 instant다.
2. 같은 시각이 두 번 존재하면 **이른 instant**만 선택한다. 늦은 반복 시각은 새 슬롯이 아니다.
3. DST 전진으로 시각이 존재하지 않으면 **같은 현지 날짜에서 목표 시각 이후 처음 존재하는 분**으로 보낸다. 예: 뉴욕 02:30이 사라진 날은 03:00이다. 03:30으로 이동시키는 Temporal `compatible`과 다르며 의도적으로 선택한 제품 정책이다.
4. 날짜 전체가 사라졌거나 그 날짜 안에 목표 이후 유효 분이 전혀 없으면 그 날짜는 **건너뛴다**. 존재하지 않는 날짜의 이메일을 다음 날 하나 더 만들지 않는다. 다음 실제 현지 날짜에서 같은 규칙을 적용한다.
5. 하루 종료는 해당 현지 날짜 다음의 첫 실제 날짜 경계다. 항상 24시간을 더하지 않는다. 다음 요약 시각도 `due+86400000`이 아니라 **다음 현지 날짜 + HH:mm**으로 계산한다.
6. 조건 모드 창은 `dueInstant ≤ now < localDayEndInstant`다. DST 뒤로 이동한 중간에 화면 HH:mm이 다시 작아져도 이미 열린 창을 닫지 않는다. 실제 예약 실행이 늦으면 창 안의 첫 작업에서 처리하며 정각 도착을 보장하는 문구를 쓰지 않는다.

Intl 사용 원칙은 UTC instant를 명시한 시간대의 날짜·시각 부분으로 변환하고, 역변환 후보를 다시 그 부분값으로 검증하는 것이다. `formatToParts`에 Gregorian 달력, Latin 숫자, `hourCycle:'h23'`을 명시한다. locale 출력 문자열을 Date로 다시 파싱하거나 호스트 `getHours()`에 의존하지 않는다. 희귀 전환까지 처리할 수 없는 변환 결과는 확인 필요로 남기고 임의 UTC 시점을 만들지 않는다. 매 사용자·매 tick마다 큰 분 단위 탐색을 수행하는 방식은 처리 비용 검토 없이 채택하지 않는다.

## 3. daily와 condition의 실제 의미

### daily: 수신 시각 이후 첫 작업에서 하루 한 번 평가

- 해당 날짜 due 이전에는 처리하지 않는다. 이후 첫 작업에서 아직 보내지 않았고 현재 유효한 항목을 **한 통에 묶는다**.
- 후보가 0이면 이메일 없이 `evaluated_empty`로 그 날짜 슬롯을 닫는다. 같은 날 나중에 도착한 항목은 다음 날 요약 후보다. 빈 검사 때마다 새 메일을 만드는 구조가 아니다.
- 성공한 요약이나 빈 평가로 닫힌 슬롯은 같은 날 다시 열지 않는다. 실패한 같은 전송 건의 재시도는 새 요약이 아니다. 발송 한도 때문에 잠시 대기하는 것은 빈 평가와 다르므로 아직 슬롯을 닫지 않는다.
- 작업이 하루 이상 멈췄다면 과거 날짜마다 누락 요약을 여러 통 재생하지 않는다. **현재 날짜의 due 이후**에 현재 유효 후보를 한 번 평가한다. 종료된 행사는 제거한다.
- 고객 문구: “선택한 시간대의 매일 HH:mm 이후 확인된 새 항목을 한 번 모아 보내요. 새 항목이 없으면 보내지 않아요.”

### condition: 수신 시작 시각 이후 처리 창에서 최근 24시간 최대 3회

- HH:mm은 **그날 이메일 처리 시작 시각**이다. 하루 한 번만 처리한다는 의미로 표시하지 않는다. 전날 이후 쌓인 후보는 창이 열릴 때, 이후 새 후보는 다음 작업에서 처리한다.
- 같은 작업 시점의 적합한 새 후보는 한 통으로 묶는다. 한 통을 보내고 나중 작업에서 새 후보가 생기면 다음 통을 보낼 수 있으며 최근 24시간 최대 3통이다. 같은 작업에서 5개 행사를 발견했다고 곧바로 5통으로 나누지 않는다.
- 3통을 채운 뒤의 새 후보는 앱에 남기고 rolling 제한이 풀린 뒤 허용된 현지 처리 창에서 검수·자격·기간을 다시 확인하여 묶는다. 자정이 지났다는 이유로 상한을 초기화하지 않는다. 만료되거나 이미 전달한 항목은 넣지 않는다.
- 고객 문구: “HH:mm 이후 조건에 맞는 새 항목을 확인할 때 알려드려요. 최근 24시간 최대 3회이며, 넘는 항목은 다음 가능한 확인 때 모아 보내요.” 실제 작업이 없으면 이메일도 실행되지 않으므로 무방문 실행 구현과 배포 증거가 별도로 필요하다.

## 4. 일자별 상한과 날짜선·설정 변경에 의한 초기화 방지

**확정한 두 방식의 제한:**

1. daily는 현지 날짜의 슬롯을 한 번 닫고 다음 요약 가드를 보존한다. 조건 모드에는 별도의 “현지 날짜당3” 카운터 제한을 추가하지 않는다. 일자는 처리 창/슬롯과 운영 이력에 사용하고, 조건 모드 UI는 최근24시간 기준이라고 표시한다.
2. condition의 새 통을 허용할 때 **사용자·이메일 채널의 최근 24시간 서로 다른 접수/불확실 시도 통수 <3**을 요구한다. 이전 통의 모드/시간대/시각이 달랐어도 기록은 유지한다. 구간은 `(now−24h, now]`이며 정확히 24시간 전의 건은 제외한다. 재시도 HTTP 요청 수는 서로 다른 통수가 아니다. daily의 새 슬롯 자체에는 별도 rolling3을 필수로 추가하지 않는다. 다시 condition으로 전환하면 과거 통수를 모두 고려한다. 자연스러운 자정에도 즉시 초기화되지 않는다. 반대로 DST로 길어진25시간 현지 날짜에는 rolling24h를 지키면서 날짜 합계가3을 넘을 수 있으므로 “현지 하루3”이라고 표현하면 안 된다.

**daily 전환 가드:** daily 슬롯을 성공/빈 상태로 닫을 때 그 슬롯의 시간대·시각 기준 **다음 현지 날짜 due**를 `digestNotBefore`로 보존한다. 그 뒤 시간대·시각·모드를 바꾸거나 동의를 껐다 켜도 이 시각을 앞당기거나 삭제하지 않는다. 새 daily 후보의 실제 처리 가능 시점은 새 due와 남아 있는 이 가드 중 늦은 시점이다. 그 시점이 새 후보 날짜의 종료 이후라면 그 날짜를 건너뛴다. 이 가드 때문에 변경 후 첫 요약은 새 HH:mm보다 늦어질 수 있으므로 계산된 “다음 확인 가능 시각”을 보여 준다. 이후 슬롯부터 새 시간대·시각을 기준으로 다음날 가드를 계산한다.

이 방식은 DST 때문에 정상적인 다음날 요약 간격이 23시간 또는 25시간일 수 있음을 허용한다. 단순히 모든 daily를 `lastSent+24h`로 막아 봄 전환일의 수신 시간을 한 시간 밀지 않는다. 최근24시간3 제한은 condition 새 통의 결정에 적용한다.

## 5. 설정 변경, 미완료 건과 소식 정체성

- 서버에서 정규화한 방식/시간대/시각/동의가 **실제로 달라졌을 때만** 예약을 다시 계산한다. 이름이나 다른 관심 설정을 저장한 no-op으로 예정 시점을 내일로 미루지 않는다.
- daily 최초 동의나 아직 소비하지 않은 설정 변경은 **현재 현지 날짜의 canonical due**와 now를 비교한다. 이미 due가 지났으면 첫 refresh/처리에서 당일 catch-up을 허용한다. 저장 요청 자체에서 전송하지 않는다. fold의 첫 시각이 지났더라도 당일 슬롯을 소비하지 않았으면 첫 처리에서 평가할 수 있지만 두 번째 발생을 별도 슬롯으로 세지 않는다. 이미 소비한 슬롯의 `digestNotBefore`와 전달 이력은 보존한다.
- condition 설정 변경은 현재 날짜의 새 창이 열려 있으면 다음 작업에서 처리 가능하다. 창 이전이면 새 due까지 기다린다. 저장 요청 자체에서 발송하지 않는다. 기존 날짜/24시간 통수와 같은 소식의 전달 이력은 초기화하지 않는다.
- 수신 해제는 즉시 대기·예약을 취소한다. 다시 켜도 **이미 접수/전달된 같은 소식은 재발송하지 않는다**. 이전에 발송되지 않았음이 확실한 취소 후보만 현재 조건으로 다시 검토할 수 있다.
- 설정 버전이 바뀌면 아직 제공사에 넘기지 않은 작업은 새 동의·창·상한을 다시 검사한다. 설정 변경 전에 예약을 잡았다는 사실만으로 옛 시간에 보낼 수 없다. 이미 제공사에 넘긴 건은 되돌릴 수 있다고 표시하지 않는다.
- 같은 소식의 전달 식별자는 `사용자 + 채널 + 소식 ID + 중요 변경 버전`이다. **날짜·시간대·HH:mm·알림 모드·설정 버전은 여기에 넣지 않는다.** 요약은 포함한 모든 소식 식별자를 연결해 condition→daily 및 daily→condition 중복을 막는다. 단순 확인일 변경은 중요 변경 버전을 만들지 않는다.
- 발송 직전 유효성·자격·필수 조건·동의를 재확인한다. 행사 종료 시점은 공식 출처의 시간대/절대 시점에 속하며 수신자의 시간대 변경으로 늘어나지 않는다. 종료 시각·시간대가 미확인인 날짜 문자열을 임의로 수신자 자정에 만료시키거나 맞춤 이메일의 확정 조건으로 보지 않는다.
- 제공사 결과가 불확실한 건은 같은 통·같은 idempotency identity로 처리하고, 시각/날짜/모드 변경으로 새 통을 만들어 우회하지 않는다. 이 문서는 제공사 재시도 구현을 대신하지 않는다.

## 고정 테스트 벡터

공통 전제: 서버 `now`는 표의 UTC instant로 주입한다. A/B/C/D는 서로 다른 소식 ID·중요 버전이다. 별도 언급이 없으면 동의·자격·출처 유효성은 충족하고 이력/예약은 비어 있다. 예상 결과는 위 정책에서 미리 도출했으며 후보 구현의 결과를 보아 바꾼 값이 아니다. 상태 판단과 UTC 시각을 함께 검증한다. PASS/FAIL 열은 아직 없으며 실제 이메일은 보내지 않는다.

## 공식 API 근거와 날짜 확인 범위

- [ECMA-402 DateTimeFormat](https://tc39.es/ecma402/#sec-createdatetimeformat): 명시적 timeZone과 hour cycle을 받으며 지원하지 않는 이름은 오류다. [formatToParts](https://tc39.es/ecma402/#sec-intl.datetimeformat.prototype.formattoparts)는 부분값 접근 근거다. 날짜·숫자·시간 형식을 고정하여 호스트 기본값과 표시 문자열 파싱을 피한다.
- [TC39 Temporal 시간대 설명](https://tc39.es/proposal-temporal/docs/timezone.html): 현지 시각이 사라지거나 반복되어 변환이 모호할 수 있음을 설명한다. 이 문서는 gap의 기본 compatible 이동과 다른 “첫 유효 분” 정책을 선택했으며 Temporal 기능을 런타임에 설치·사용했다는 주장이 아니다.
- 2026-09-12T13:33:28Z에 **Node v24.18.0 / ICU78.3 / tz2026a의 내장 Intl 순방향 표시**로 표의 Seoul, Kathmandu, Kiritimati, Pago Pago, 뉴욕 전환, Lord Howe 전환, Apia 날짜 건너뜀에 해당하는 UTC instant들을 확인했다. 예: 뉴욕 07:00Z→03:00, Lord Howe15:30Z→02:30, Apia2011-12-30T10:00Z→12월31일00:00. 이는 시간대 산술의 보조 확인이며 위 알림 스케줄러나 전달 규칙의 테스트 PASS가 아니다. 배포 런타임의 시간대 데이터 버전도 별도로 확인해야 한다.

## 검증 인계

필수38개 ID는 T01–T12, M01–M10, E02–E04/E06–E11, I01–I07이다. 별도 비채택 E01/E05를 포함하면 문서에는 총40개 ID가 있으며 둘을 실패/분모에 넣지 않는다. root의 정책 선택 뒤, 알림 구현 출력 관찰 전에 고정한 에이전트 검증 사례다. 순수 시간 계산은 고정 now로, 상한·동시성·슬롯/소식 이력은 격리된 로컬 데이터로 검증할 수 있다. 필수 벡터의 기대 시각·상태·통수 중 하나라도 다르면 실패/설계 차이로 기록하고 사례를 제거하지 않는다. 실제 사용자 연구, 실제 무방문 처리, 제공사 접수나 수신함 도착의 증거를 대신하지 않는다. 고정 게이트 점수는 이 설계 문서만으로 변경하지 않는다.
