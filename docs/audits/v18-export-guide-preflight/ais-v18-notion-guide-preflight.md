1. 실제 Notion UI의 계정·작업 공간과 새 QA 페이지를 만들 권한을 확인한다. 기존 개인 페이지 내용은 업무와 무관하면 열지 않는다.
2. 새 QA 페이지의 고유 URL과 시작 전 상태를 기록하고, 위 5단계를 UI에서 순서대로 수행한다. 메뉴가 원문과 다르면 실제 보이는 명칭과 대응을 기록한다.
3. 필터 없는 표·보드의 3개 업무, 정렬, 저장 필터, 카드 메모·상태 변경을 UI에서 확인한다. 실패/복구/재시도가 있으면 그대로 남긴다.
4. 필요하면 이후 해당 **새 QA URL만** fetch하여 DB/보기/행을 read-only 대조한다. rows/view 조회는 UI 상태의 보조 증거이며 단계 수행 이력을 대체하지 않는다.
5. 재현 일시, Site 가이드 ID/소스 hash, Notion QA URL, UI 액션 요약, 단계별 사진·결과 확인, 남은 차이를 보고한다. 에이전트 실제 수행인지 실사용자 연구인지 명확히 표시한다.

아직 QA 생성·실제 수행·결과 확인은 하지 않았으므로 **6.3.4는 UNVERIFIED 유지**다. 사전 점검의 결론은 ‘MCP 연결과 필요한 도구는 제공되지만 현재 Notion UI 인증이 없어 전체 가이드 UI 재현을 시작하지 못했다’이다. 사용자 로그인 이후에도 목적지 편집 권한과 실제 단계·결과는 별도로 확인해야 한다.

## 최종 상태 보완: root의 실제 UI 인증 관찰

root가 사전 점검 중 다음 실제 UI 경로를 보고했다: IAB의 Notion URL → 마케팅 페이지 → 로그인 → ChatGPT 선택 → `auth.openai.com/log-in`의 이메일 입력 화면. 기존 로그인 세션은 없었다. root는 이메일·인증정보를 입력하거나 계정을 생성하지 않았고, 새 문서·DB를 만들거나 기존 자료를 변경하지 않았다.

root는 Notion 로그인으로 돌아가 **탭 19 handoff**를 준비했으며 `open_in_codex`는 queued 상태, 사용자 로그인 요청 1건은 pending이라고 보고했다. Notion 네이티브 앱은 inventory에 없었다는 보고도 받았다. 이 항목은 root의 UI 수행 결과를 전달받아 기록한 것이며, 이 사전 점검자가 브라우저나 화면을 독립적으로 조작·판독한 것은 아니다.

따라서 MCP의 `fetch(self)`와 search 성공은 **연결된 API 인증**의 증거이고, 브라우저의 Notion 로그인·UI 조작 가능성을 입증하지 않는다. API가 쓰기를 지원한다는 이유로 UI 단계를 우회해 문서나 DB를 생성하지 않는다. 이미 대기 중인 사용자 로그인 요청을 중복 요청하지 않으며, 로그인 이후 root가 실제 UI 재현을 재개할 때까지 위 고정 입력·단계·성공 기준을 보존한다.
