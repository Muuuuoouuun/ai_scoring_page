## Remaining part of original P2: hide → save before refresh completes

Sources: [Notifications.tsx:8](/Users/bigmac_moon/dev/ai_score/site/components/Notifications.tsx:8), [MyWorkspace.tsx:17](/Users/bigmac_moon/dev/ai_score/site/components/MyWorkspace.tsx:17), [Preferences.tsx:8](/Users/bigmac_moon/dev/ai_score/site/components/Preferences.tsx:8), [workspace API:83–90](/Users/bigmac_moon/dev/ai_score/site/app/api/workspace/route.ts:83).

`onChanged()` increments MyWorkspace's fetch version; it does not await or gate the full-records refresh. MyWorkspace does not enter its loading state again on this refresh. Before that request resolves, the user can enter Settings, where the previous records still initialize an enabled full-save form. The new Preferences effect fixes the state **after** the fetch arrives, but cannot repair a full save that already replaced hiddenTopics on the server.

Isolated handler replay uses the exact state ordering: read settings → hide an owned notice → submit the previously loaded full settings payload with only display name changed. The stale save still returns **200**, hiddenTopics returns to empty, and **one hidden notice reappears**. In contrast, reading the refreshed settings before saving leaves it hidden. I did not perform browser timing interactions; this result combines a source-visible unguarded interval with a reproduced server effect, and is not a claim about how often users encounter the interval.

Smallest faithful completion: do not permit a full Settings save until its required refresh succeeds, or make normal Settings updates preserve the current server hiddenTopics unless the user explicitly changes that field. A field patch or explicit hidden-topic intent also handles out-of-order requests. Preserve explicit “다시 받기” functionality. Test with a deliberately delayed workspace GET, hide, immediate Settings navigation and save; also test failed refresh so stale data cannot silently win.
