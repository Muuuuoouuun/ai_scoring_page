# AI 기능 발견·리뷰 설계

## 목표

기존 도구 카탈로그에 흩어진 기능 정보를 독립적인 “AI 기능” 경험으로 확장한다. 사용자는 이미 아는 기능을 검색할 수 있고, ChatGPT·Gemini·Claude 등에서 놓치기 쉬운 실용 기능도 자연스럽게 발견할 수 있어야 한다.

첫 공개 범위는 주요 AI 서비스 8개와 약 80~100개 기능이다. 개별 명령어나 API 옵션을 망라하지 않고, 알았을 때 실제 사용 방식이 달라지는 기능만 선별한다.

## 확정된 제품 방향

- 정보 성격은 하이브리드다. 공식 문서로 확인한 사실을 기본으로 두고, 실제 계정에서 직접 재현한 경우에만 별도의 사용 리뷰를 표시한다.
- 새 `/features` 허브, 개별 `/features/[id]` 리뷰, 기존 `/tools/[id]` 상세를 양방향으로 연결한다.
- 허브는 “발견 + 검색” 혼합형이다. 상단은 대표·숨은 기능을 큐레이션하고, 중간은 목적별 탐색, 하단은 전체 검색·필터를 제공한다.
- 첫 공개는 ChatGPT, Gemini, Claude, NotebookLM, Perplexity, Microsoft Copilot, Grok, Cursor를 다룬다.
- 개발자 전용 세부 옵션은 제외하되, Agent Builder·Claude Code `/goal`처럼 대중적 관심이 높고 사용 방식에 큰 영향을 주는 기능은 “고급” 배지로 포함한다.
- 공식 명칭이 아닌 표현은 검색 별칭으로만 사용한다. 예를 들어 “클로드의 예언”은 기능명으로 등록하지 않고 예약 작업 후보를 안내한다.

## 사용자 경험

### 1. 기능 허브 `/features`

페이지 순서는 다음과 같다.

1. 목적형 검색: “회의 내용을 자동으로 정리하고 싶어요”처럼 자연어로 검색한다.
2. 지금 볼 기능: 서비스 발표·출시 상태와 무관하게 편집자가 선정한 대표 기능을 보여준다.
3. 숨은 꿀기능: 널리 알려지지 않았지만 실용성이 높은 기능을 보여준다.
4. 목적별 묶음: 조사·리서치, 프로젝트·기억, 문서·데이터 제작, 이미지·영상, 자동화·행동, 음성·비전, 코딩·에이전트로 탐색한다.
5. 전체 기능: 서비스, 목적, 무료 이용 가능 여부, 기기, 출시 상태, 대표/숨은/고급 배지로 필터한다.

“인기”, “최고”, “사용자들이 많이 쓰는”처럼 근거가 필요한 표현은 실제 데이터 없이 사용하지 않는다. 큐레이션은 “추천”이 아니라 “지금 볼 기능”으로 표시하고 선정 기준을 공개한다.

### 2. 기능 카드

각 카드는 다음 정보만 우선 노출한다.

- 서비스 로고와 서비스명
- 공식 기능명과 이해하기 쉬운 한국어 이름
- 한 문장 가치
- 대표 기능, 숨은 기능, 고급 기능 중 하나
- 목적 태그 최대 2개
- 플랜·기기·베타 등 가장 중요한 이용 조건 최대 2개
- 공식 확인일

카드에서 세부 조건을 모두 펼치지 않는다. 정보 밀도가 과해지지 않도록 나머지는 상세 페이지로 보낸다.

### 3. 기능 상세 `/features/[id]`

상세 페이지는 다음 순서로 읽힌다.

1. 공식 기능명, 서비스, 대표/숨은/고급 분류, 상태 배지
2. 30초 요약: 언제 유용한지, 일반 기능과 무엇이 다른지, 가장 중요한 주의점
3. 실제 사용 사례 2~4개
4. 시작 방법 3~5단계
5. 이용 조건: 플랜, 기기, 지역·언어, 계정·관리자 조건, 출시 상태
6. 직접 사용 리뷰: 검증한 경우에만 테스트 날짜·환경·입력·관찰 결과·장단점 표시
7. 같은 목적의 다른 서비스 기능 비교
8. 관련 기능과 해당 서비스 상세 링크
9. 공식 출처와 확인일
10. 사용자 경험과 정보 수정 제안

직접 재현하지 않은 경우에는 빈 점수 대신 “직접 실행 확인 전 · 공식 문서 정보”라고 표시한다. 편집 리뷰와 사용자 후기는 합산하지 않는다.

### 4. 기존 서비스 상세 `/tools/[id]`

현재의 간단한 기능 표는 유지하되, 새 기능 데이터가 있는 서비스에는 다음을 추가한다.

- 대표 기능 3개
- 숨은 기능 3개
- 전체 기능 수와 `/features?service=<id>` 링크
- 기능별 독립 리뷰 링크

기존 `catalog.json`의 기능은 검색·유사 도구 계산을 위해 보존한다. 새 기능 데이터와 이름이 같은 항목은 새 데이터의 요약을 우선 사용하되, 기존 API 응답 형식은 깨지지 않게 유지한다.

## 정보 구조와 데이터 모델

검수된 기능 데이터는 `site/data/features.json`에 정적 콘텐츠로 저장하고 `site/lib/features.ts`가 타입·검색·관계를 제공한다. 기능 데이터는 서비스 카탈로그와 분리해 갱신 단위를 작게 유지한다.

각 기능 항목은 다음 필드를 가진다.

- `id`, `toolId`, `officialName`, `koreanName`, `aliases`
- `oneLineValue`, `summary`, `useCases`, `gettingStarted`
- `purposeTags`, `audienceTags`, `prominence`
- `maturity`, `plans`, `devices`, `regions`, `languages`, `requirements`
- `limitations`, `safetyNotes`
- `equivalenceGroup`, `relatedFeatureIds`
- `sourceUrls`, `checkedAt`
- `handsOn`: `status`, `checkedAt`, `environment`, `method`, `observations`, `strengths`, `caveats`

`prominence`는 `flagship`, `hidden`, `advanced` 중 하나다. `handsOn.status`는 `unverified`, `verified`, `blocked` 중 하나이며, 공식 사실 지원 여부와 별개다.

같은 목적의 기능은 이름 문자열이 아니라 `equivalenceGroup`으로 연결한다. 예를 들어 Gemini Deep Research, ChatGPT Deep Research, Claude Research는 `deep-research` 그룹에 속하지만 서로 동일한 기능이라고 표현하지 않는다.

## 검색과 분류

검색은 공식명, 한국어 이름, 별칭, 한 문장 가치, 사용 사례, 목적 태그를 대상으로 한다. 기존 도구 검색과 동일하게 자연어 목적을 우선 해석하되, 기능 검색 결과는 도구 순위가 아니라 기능 관련도로 정렬한다.

공식 명칭이 불확실한 사용자 표현은 별칭 사전에서 후보로 연결한다.

- “슬래시 골” → Claude Code `/goal`
- “클로드 예언/예언 기능” → 자동 확정하지 않고 Claude Scheduled tasks 후보 설명
- “제미나이 스파크” → 공식 자료에서 확인한 후보만 제시하고 사용자가 제품을 구분할 수 있게 설명
- “에이전트 빌더” → GPTs, ChatGPT Workspace Agents, OpenAI Agent Builder, Agents SDK/API를 별도 항목으로 구분

별칭 검색은 후보를 찾게 할 뿐, 비공식 표현을 화면의 제목이나 사실로 승격하지 않는다.

## 출처와 상태 관리

- 기능 지원, 이용 조건, 출시 상태는 제공사의 공식 제품 문서·도움말·발표만 근거로 삼는다.
- 각 기능에 독립적인 확인일과 하나 이상의 공식 URL을 저장한다.
- 공식 문서가 서로 충돌하면 한쪽을 선택해 단정하지 않고 “계정·롤아웃 확인 필요” 상태와 충돌 근거를 표시한다.
- 베타, 미리보기, 단계적 출시, 레거시, 종료 예정을 별도 상태로 구분한다.
- 종료된 기능은 검색 기본 결과에서 제외하고 직접 URL이나 “종료됨” 필터에서만 보여준다.
- 공식 피드 변경은 검토 후보만 만들며 기능 사실을 자동 덮어쓰지 않는다.

조사에서 확인한 중요한 예시는 다음과 같다.

- Claude Code `/goal`은 완료 조건을 별도 평가하며 작업을 지속하는 공식 기능이다.
- “Claude의 예언 기능”이라는 공식 명칭은 확인되지 않았고, 예약 작업의 오청 가능성이 가장 높다.
- OpenAI의 노드형 Agent Builder는 현행 사용자용 기능들과 구분해야 하며, 공식 문서상 레거시·종료 예정 상태를 표시해야 한다.
- 문서 간 플랜 표기가 충돌하는 기능은 이용 가능을 단정하지 않는다.

## 사용자 리뷰와 커뮤니티

기능 상세의 “사용 경험 남기기”는 기존 커뮤니티 흐름을 재사용한다. 게시물은 기존 `tool_id`와 함께 선택적인 `feature_id`를 가질 수 있다.

- 공식 기능 설명과 사용자가 쓴 경험은 시각적으로 분리한다.
- 사용자 평점은 도구 전체 평점과 기능 경험을 혼합 집계하지 않는다.
- 기능 후기에는 사용일, 플랜, 기기 또는 환경을 받는다.
- 정보 수정 제안은 공식 출처 URL과 확인 내용을 받으며 검수 전에는 기능 데이터에 반영하지 않는다.
- 로그인, 소유권, 수정·삭제, 신고, 계정 격리 규칙은 기존 커뮤니티 API와 동일하게 유지한다.

## 컴포넌트 경계

- `FeatureHub`: 큐레이션, 목적 탐색, 검색·필터의 조합만 담당한다.
- `FeatureCard`: 목록에 필요한 최소 정보만 렌더한다.
- `FeatureFilters`: URL 검색 파라미터와 필터 상태를 동기화한다.
- `FeatureDetail`: 기능 본문 섹션을 조합한다.
- `FeatureAccessFacts`: 플랜·기기·지역·출시 상태를 표시한다.
- `HandsOnReview`: 직접 검증 상태와 관찰 결과만 표시한다.
- `EquivalentFeatures`: 같은 `equivalenceGroup`의 기능을 비교한다.
- `FeatureCommunity`: 기능별 후기와 제안으로 기존 커뮤니티를 연결한다.
- `features.ts`: 데이터 검증, 검색, 필터, 관련 기능 계산을 담당하는 순수 모듈이다.

각 컴포넌트는 전체 원시 JSON이 아니라 필요한 타입만 받는다. 검색·관계 계산을 렌더링 코드에 넣지 않는다.

## 오류·빈 상태

- 존재하지 않는 기능 ID는 기존 404 화면으로 보낸다.
- 필터 결과가 없으면 조건 초기화와 목적형 검색 예시를 제공한다.
- 공식 출처가 없거나 확인일이 없는 항목은 빌드 검증에서 실패시킨다.
- 서비스는 있지만 기능 데이터가 없는 경우 기존 기능 표를 유지하고 “심층 리뷰 준비 중”이라고 표시한다.
- 사용자 후기 API가 실패해도 공식 기능 본문은 정상 표시하고, 후기 영역만 재시도 상태를 보여준다.

## 반응형·접근성

- 데스크톱 상세는 본문과 이용 조건 사이드바의 2열, 모바일은 본문 우선 1열이다.
- 카드와 필터는 키보드로 모두 접근할 수 있고, 상태는 색뿐 아니라 텍스트 배지로 구분한다.
- 상세 목차 앵커는 고정 헤더 아래에 가려지지 않는다.
- 표 형태의 비교는 390px에서 가로 스크롤에 의존하지 않도록 카드 목록으로 전환한다.
- 공식 링크는 새 창 동작과 출처 성격을 보조 텍스트로 알린다.

## 검증

구현 전 실패 테스트를 먼저 추가한다.

- 데이터 스키마: ID·서비스 참조·출처·확인일·상태·관계 그룹 무결성
- 검색: 공식명, 한국어명, 별칭, 목적 문장, 비공식 명칭 후보, 제외 조건
- 필터: 서비스, 목적, 무료, 기기, 상태, 대표/숨은/고급의 조합
- 상세: 공식 사실과 직접 사용 리뷰의 분리, 미검증 상태, 출처 링크
- 관계: 같은 그룹의 비교와 관련 기능 연결, 동일하다고 오인시키는 문구 방지
- 커뮤니티: `feature_id` 검증, 계정 소유권, 수정 시 대상 불변, 도구 전체 평점과 분리
- 회귀: 기존 도구 탐색·검색·유사 도구·비교·커뮤니티·모바일 내비게이션

타입 검사, 전체 Node 테스트, Sites 빌드를 실행하고 데스크톱과 390px에서 허브 검색→필터→상세→유사 기능→서비스 상세→후기 작성 진입을 확인한다.

## 제외 범위

- 모든 슬래시 명령과 API 파라미터의 백과사전식 수록
- 공식 근거 없는 소문·실험 기능
- 직접 실행하지 않은 기능의 편집 점수·장단점 생성
- 사용자 후기와 공식 기능 지원 여부의 자동 혼합
- 외부 서비스를 자동 조작하거나 계정 연결이 완료된 것처럼 표시하는 기능
- 기능 변경을 검토 없이 자동 반영하는 크롤러
