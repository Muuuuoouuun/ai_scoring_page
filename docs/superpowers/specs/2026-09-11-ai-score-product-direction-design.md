**첫 고객은 ‘반복적으로 리서치·문서·콘텐츠 기획을 하는 한국어 실무자’로 가정한다.** 직무는 1인 마케터·기획자·작은 팀의 운영 담당자를 우선 후보로 둔다. AI를 이미 조금 사용하고, 기존 구독을 유지할지 새 도구를 추가할지 고민하는 사람이 첫 실험에 적합하다는 가설이다. 실제 모집 가능성과 문제의 강도를 인터뷰에서 확인한다.

소규모 팀에 속한 개인도 초기 대상에 포함하지만, 팀 공용 계정·관리자 승인·좌석 결제는 첫 출시 범위에 포함하지 않는다. 개발자용 모델·API 성능 비교, 전문 영상 제작, 전사 구매 관리는 업무와 판단 기준이 달라 후속 검증 대상으로 둔다.

| 첫 업무 시나리오 | 사용자가 완성하려는 것 | 비교할 핵심 조건 |
|---|---|---|
| 자료 조사 → 근거 있는 요약 | 출처를 확인할 수 있는 조사 메모 | 출처 정확성, 사실 누락, 한국어 요약, 확인에 든 시간 |
| 자료 묶음 → 보고서 초안 | 수정해 제출할 수 있는 문서 | 파일 처리, 근거 반영, 문서 구조, 수정량, 내보내기 |
| 조사 메모 → 콘텐츠 기획안 | 대상과 채널에 맞는 기획 초안 | 요구 조건 반영, 한국어 표현, 사실 유지, 반복 수정 편의 |

세 업무는 초기 후보이며, 인터뷰에서 한 업무의 수요만 뚜렷하면 그 업무부터 운영한다. 이미지·영상 생성은 기획 흐름에서 요구가 반복적으로 확인될 때 추가한다.

**제품을 관통하는 기본 단위는 ‘업무에 대한 선택 기록’이다.** 제품 페이지는 정보의 기준점으로 유지하되, 사용자 경험은 수행할 업무에서 시작한다.

1. 수행할 업무와 필요한 결과물을 선택한다.
2. 예산, 필수 기능, 현재 사용하는 도구를 입력한다. 조건 없이 둘러보기도 가능하게 한다.
3. 후보 2~3개의 추천 이유·제약·테스트 근거를 비교한다.
4. 기존 도구 유지, 새 도구 시험, 전환, 보류 중 선택과 이유를 저장한다.
5. 사용 후 결과를 짧게 기록하고, 공개할 내용은 별도로 선택한다.
6. 관련 기능이나 조건이 달라지면 이전 선택을 다시 검토한다.

비교 내용을 읽는 데 가입을 요구하지 않는다. 선택을 저장하거나 내 도구 소식을 받으려는 시점에 계정을 제안한다. 사용자의 실제 구독·사용 여부는 수동 입력 또는 자기보고로 표시한다.

**선택 카드에는 다음 일곱 가지를 남긴다.** 업무, 필수 조건, 기존 도구, 검토한 후보, 선택과 이유, 근거의 확인일, 이후 결과다. 금액·내부 업무·개인 메모는 기본 비공개다. 공개 전에는 공개될 내용을 미리 보여준다.

가상 예시: ‘매주 한국어 조사 보고서를 작성한다. A를 이미 구독 중이고 PDF 처리가 필요하다.’ 결과는 ‘A 유지 + B 시험’일 수 있다. B를 시험하는 이유, 확인되지 않은 조건, 원래 업무에 투입해 볼 작은 과제를 함께 제시한다. 실제 제품 추천이나 성능 주장에 해당하지 않는 예시다.

**추천의 특별한 결과로 ‘현재 도구로 충분함’과 ‘판단 보류’를 인정한다.** 기존 도구의 지원 조건이 확인되면 먼저 활용 방법을 보여준다. 추가 도구는 기대되는 이점과 비용·학습 부담을 함께 설명한다. 필수 조건을 충족하는 후보가 없으면 조건을 임의로 완화하지 않고, 어떤 조건 때문에 결과가 없는지 표시한다.

추천은 초기에는 조건 필터와 편집자가 검토한 규칙으로 구현하는 방향을 제안한다. AI는 질문을 조건으로 정리하거나 근거를 요약하는 데 활용할 수 있다. 추천 이유는 확인한 자료와 연결하고, 공개하지 않은 내부 규칙이나 검증되지 않은 성공 확률로 설명하지 않는다.

**두 번째 핵심 경험은 ‘내 선택에 영향을 주는 변화’다.** 업데이트는 제품·기능·요금제·업무와 연결한다. 기존 선택 이유에 변화가 생겼을 때 사용자가 다시 검토할 수 있게 한다.

| 변화의 예시 — 모두 가상 | 사용자에게 보여줄 내용 | 적절한 다음 행동 |
|---|---|---|
| 사용 도구의 내보내기 제한 변경 | 어떤 요금제와 파일 형식이 영향을 받는지 | 해당 조건 확인 |
| 기존 도구에 필요한 기능 추가 | 현재 플랜에 제공되는지, 테스트 여부 | 기존 도구에서 먼저 시험 |
| 시험 중인 후보의 가격 변경 | 확인된 새 가격과 적용 시점 | 저장한 비교 다시 열기 |
| 예전에 포기한 기능이 개선됐다는 발표 | 발표 내용과 아직 확인하지 못한 성능 | 재테스트 결과 기다리기 |

‘발표됨·일부 제공·일반 제공’은 출시 상태다. ‘공식 자료 확인·직접 테스트·재확인 필요’는 검증 상태다. 두 축을 따로 저장한다. 일반 제공 중이면서 테스트 전일 수 있고, 베타 단계에서 직접 시험한 기능일 수도 있다.

첫 출시에는 내 도구함의 주간 변경 목록과 변경 유형 필터를 제공한다. 선택 이유를 자동 해석해 정밀 알림을 보내는 기능은 후속 단계다. 의미 있는 변경이 없는 주에는 새 소식을 억지로 만들지 않는다. 외부 이메일·푸시 브리핑은 별도 수신 설정과 운영 여력이 확인된 뒤 확장한다.

**스코어링의 기준 단위는 ‘도구 × 업무 × 요금제·버전 × 평가일’로 정한다.** 같은 도구라도 조사와 글쓰기의 결과가 다를 수 있다. 모델 자체의 벤치마크를 해당 모델을 사용하는 앱 전체의 평가로 옮기지 않는다. Artificial Analysis도 모델·API 엔드포인트·시스템을 구분해 평가 범위를 설명한다. [Artificial Analysis 공식 방법론](https://artificialanalysis.ai/methodology).

| 평가 정보 | 초기 표시 방식 | 해석 원칙 |
|---|---|---|
| 실무 테스트 | 항목별 1~5점, 수행한 과제, 결과 사례 | 같은 업무와 비교 조건 안에서 읽는다 |
| 사용자 경험 | 개별 후기, 사용 시점, 요금제, 사례 수 | 자기보고와 운영진 테스트를 구분한다 |
| 내 조건 적합성 | 필수 조건 충족·미충족·미확인, 추천 이유 | 미확인은 0점으로 바꾸지 않는다 |
| 관심도 | 측정 기간과 활동 종류가 명시된 별도 정보 | 조회·저장 수를 성능이나 만족도로 해석하지 않는다 |
| 근거 상태 | 확인일, 테스트 수, 검토자, 재확인 필요 여부 | 성능 점수와 별도로 보여준다 |

첫 출시에는 실무 테스트·후기·조건 적합성을 우선 제공한다. 트렌드 순위는 이용량이 적으면 변동이 크므로 후속 단계로 둔다. 전 분야를 합친 종합 순위와 개인 적합성 백분율은 제공하지 않는 방향이다.

**실무 테스트 v0.1은 작은 공통 과제를 반복 수행하는 방식으로 시작한다.** 한 업무에 대표 과제 3개를 만들고, 각 도구를 과제당 3회 실행하는 안을 제안한다. 이는 통계적으로 충분한 표본이라는 뜻이 아니라 변동과 실패 사례를 확인하기 위한 초기 운영안이다. 테스트 비용과 변동성을 보고 횟수를 조정한다.

| 결과 품질 | 사실·출처 정확성, 요구 사항 충족, 누락 | 요구 사항 체크 결과와 오류 사례 |

| 비용 대비 효용 | 정해진 작업량에서 필요한 플랜·사용량 | 확인한 가격·조건·작업량 가정과 확인일 |
| 작업 연결성 | 입력 파일·연동·내보내기 품질 | 성공·실패한 형식과 제한 |

각 항목은 과제별로 1점·3점·5점의 관찰 기준을 먼저 작성하고 2점·4점은 그 사이로 정의한다. 예를 들어 결과 품질은 ‘필수 요구 사항을 수행하지 못함 / 주요 결과는 얻었으나 상당한 수정 필요 / 사전 정의한 필수 기준 충족’으로 기준을 잡고, 과제에 맞는 체크 항목을 붙인다. 중대한 출처 오류 같은 실패 조건은 점수와 별도 표시한다. 미실시·측정 불가 항목은 점수 없이 이유를 남긴다.

입력 자료, 공통 목표, 프롬프트, 설정, 도구별 조정, 버전·플랜, 평가일을 기록한다. 기본 사용과 숙련자 최적화 결과를 함께 다룬다면 서로 구분한다. 가능한 범위에서 일부 결과를 다른 검토자가 재검토하고, 혼자 평가했다면 그 사실을 공개한다.

초기 화면에서는 항목별 점수와 근거를 먼저 제공한다. 100점 종합 점수는 항목 간 중복과 가중치에 따른 순위 변화를 검토한 뒤 도입한다. 같은 과제·평가 기준을 충족한 결과만 비교하고, 조건이 다른 과거 점수와는 직접적인 상승·하락을 표시하지 않는다. 중요한 제품 변경이 있으면 기존 평가에 ‘재확인 필요’를 붙인다.

후기 집계 기준도 조사 전 임의로 신뢰 수준을 약속하지 않는다. 파일럿에서는 개별 경험과 건수를 노출하고, 집계 평점·순위는 표본과 운영 기준을 마련한 뒤 추가한다. 긍정·부정 경험 모두 동일한 양식으로 수집하고, 업체 관계자·제공받은 혜택은 표시한다.

**커뮤니티는 짧은 사용 결과 기록에서 시작한다.** 사용 후 ‘계속 사용 / 추가 시험 / 중단’과 한 줄 이유를 먼저 받는다. 기록을 공개 후기로 확장할 때 업무, 플랜, 사용 시점, 잘된 점, 한계, 가능한 결과 예시를 추가하게 한다.

초기 글 유형은 실사용 후기와 도구 선택 질문 두 가지다. 활용 방법과 여러 도구의 조합은 후기 양식 안에 선택 항목으로 포함한다. 모든 게시물은 적어도 하나의 도구 또는 업무 시나리오와 연결한다. 회원의 실제 경험을 대신 만들어 게시하지 않는다. 운영진이 직접 시험한 내용은 운영진 콘텐츠로 표시한다.

초기 참여 동기는 다음 세 가지로 설계한다. 선택 질문에는 비교 근거를 제공하고, 사용 결과 기록에는 다음 추천을 위한 맥락이 쌓이며, 정보 오류 제보에는 반영 결과를 알려준다. 복잡한 포인트 제도는 실제 기여 방식이 확인된 뒤 검토한다. 신고와 오류 제보는 첫 출시부터 받을 수 있게 하고, 운영진이 수동 처리한다.

**출시 범위는 ‘첫 선택을 돕고, 선택 이후 한 번 더 돌아올 이유를 제공하는 것’에 맞춘다.** 운영진이 기본 정보와 비교를 제공해 회원 후기가 없어도 사용할 수 있게 한다.

| 단계 | 포함할 범위 | 완료 또는 다음 단계 판단 기준 |
|---|---|---|
| 개발 전 파일럿 | 실제 선택 문제 인터뷰, 수작업 비교, 개인별 선택·결과 기록, 관련 변경 전달 실험 | 선택 도움과 재방문 이유를 실제 사례로 확인 |
| 첫 공개 웹 버전 | 업무 필터, 도구 상세, 2~3개 비교, 규칙 기반 추천, 선택 기록, 내 도구 상태, 주간 변경 목록 | 사용자가 혼자 비교→저장→변경 확인까지 수행 가능 |
| 첫 공개 웹 버전의 커뮤니티·운영 | 후기·질문·댓글, 신고·오류 제보, 수동 게시물 관리, 출처·확인일·수정 이력 | 신고·수정과 게시물 분류를 운영자가 처리 가능 |
| 검증 후 확장 | 공개 도구 조합, 외부 주간 브리핑, 선택 이유에 따른 변경 안내, 작업 방법 콘텐츠 | 첫 이용 이후 재사용과 관련 수요 확인 |
| 별도 사업 가설 검증 후 | 팀 공용 비교·승인, 정교한 구독 관리, 고급 개인화 | 반복적인 팀 요청·관리 문제·지불 의향 확인 |

첫 공개 버전에는 기본 정보 15~20개 도구, 직접 테스트 6개 내외, 업무 시나리오 최대 3개를 운영 목표의 시작점으로 제안한다. 모두 실제 운영 시간에 맞춰 줄일 수 있다. 원안의 30~50개 도구보다 좁게 시작해, 정기 확인을 유지할 수 있는지 먼저 본다. 숫자를 채우는 것 자체를 출시 조건으로 삼지 않는다.

뉴스·행사는 소식 피드 안에서 유형을 나눈다. 초기에는 다루는 업무와 등록 도구에 관련된 내용을 선별한다. 행사는 대상, 수준, 일정·시간대, 언어, 비용, 신청 마감, 공식 신청 링크를 갖추고 소량 발행한다. 자체 티켓 결제, 실시간 채팅, 자동 구독 해지, 네이티브 앱은 초기 범위 밖이다.

**메뉴는 사용자가 하려는 행동에 맞춘다.** 첫 화면은 가입 전과 도구 저장 후의 우선순위를 달리한다.

| 메뉴 | 역할 | 주요 행동 |
|---|---|---|
| 발견 | 업무별 선택 가이드와 추천 진입 | 업무 선택, 비교 시작 |
| 도구 | 제품별 정보·평가·후기·변경의 기준 페이지 | 조건 필터, 도구 비교 |
| 소식 | 도구 변경·선별 뉴스·행사 | 관심 도구로 필터, 관련 도구 열기 |
| 경험 | 실사용 후기와 선택 질문 | 내 상황과 비슷한 경험 확인 |
| 내 도구함 | 저장한 비교·선택·사용 상태·개인 메모 | 선택 재검토, 결과 기록, 변경 확인 |

첫 방문자는 ‘무슨 일을 하려고 하나요?’와 업무별 비교 사례를 먼저 본다. 내 도구를 등록한 사용자는 해당 도구의 주요 변화와 진행 중인 선택을 먼저 본다. 저장이 없는 사용자의 화면에는 편집자가 만든 대표 비교를 제공한다. 모바일 웹에서 읽기·비교·저장·짧은 후기 작성을 마칠 수 있게 한다.

**정보 운영은 제품 기능에 포함한다.** 수집량보다 유지할 수 있는 정확도와 범위를 기준으로 확장한다.

| 운영 대상 | 제안하는 확인 방식 | 문제 발견 시 처리 |
|---|---|---|
| 깊이 평가하는 핵심 도구 | 공식 가격·주요 제한을 주 1회 점검하고 변경 신호 시 추가 확인 | 관련 필드와 추천 규칙 재검토 |
| 나머지 기본 정보 | 월 1회 확인을 시작 기준으로 사용 | 기한 초과 시 마지막 확인일과 재확인 필요 표시 |
| 신규 업데이트 | 공식 원문, 적용 대상, 발표·적용일 확인 | 미확인 사실과 편집 해석을 구분 |
| 실무 평가 | 주요 모델·기능·플랜 변경 시 영향 판단 | 기존 결과를 보존하고 재평가 상태 표시 |
| 사용자 후기 | 필수 맥락 확인, 신고·이해관계 표시 | 정책에 따라 보류·수정 요청·처리 결과 안내 |

위 주기는 제공을 약속하는 서비스 수준이 아니라 초기 운영 가설이다. 매주 실제 소요 시간을 기록해 조정한다. 소식이 늦더라도 확인하지 않은 가격이나 지원 여부를 확정적으로 발행하지 않는다.

정보에는 원문 URL, 출처 유형, 발표일, 적용일, 마지막 확인일, 관련 도구·플랜, 검증 상태를 붙인다. AI로 수집 후보·중복 정리·번역·요약 초안을 만들고, 가격·정책·지원 조건·점수는 사람이 확인한 뒤 반영한다. 원문과 이미지 이용조건을 확인하고, 필요한 범위의 요약과 원문 연결을 기본으로 한다.

오류가 수정되면 현재 정보와 수정 이유를 남긴다. 어떤 선택 기록이 이전 정보를 참조했는지 확인할 수 있게 하고, 첫 단계에서는 운영자가 영향을 검토한다. 개인 메모와 도구 사용 내역의 공개·수정·삭제는 사용자가 통제한다.

기획상 연결해야 할 정보는 업무 시나리오, 도구, 기능·요금제, 평가, 변경, 선택 기록, 사용 결과, 후기·질문, 출처다. 구체적인 데이터베이스 구조와 기술 스택은 제품 검증 이후 별도 명세에서 결정한다.

**검증은 ‘선택할 때 유용한가’와 ‘선택한 뒤에도 유용한가’를 따로 본다.** 아래 6주는 개발 완료 일정이 아니라 인터뷰와 수작업 서비스를 포함한 파일럿 예시다. 실제 모집 시점에 맞춰 조정한다.

| 시점 | 실행할 실험 | 확인할 것 |
|---|---|---|
| 1주차 | 최근 도구 선택 경험이 있는 실무자 약 10명 인터뷰 | 반복되는 업무, 기존 해결 방법, 선택을 망설인 조건 |
| 2주차 | 동일 업무군의 파일럿 참가자 약 20명에게 비교 제공 | 후보·근거 이해, 선택 또는 보류의 이유, 첫 사용 계획 |
| 3주차 | 비교 제공 7일 후 결과 수집 | 사용 여부, 도움을 받은 지점, 수정 부담, 선택 변경 |
| 4~5주차 | 관련 변화가 있는 참가자에게 변경 정보 제공 | 관련성, 재방문, 재검토 행동; 관련 변화가 없으면 따로 기록 |
| 6주차 | 각 참가자의 비교 제공일 기준 28일 관찰 완료 | 재사용·재방문과 계속 필요로 하는 기능 |

인터뷰는 ‘이 서비스가 있으면 쓰겠는가’보다 최근 실제 선택의 경과를 듣는다. 무엇을 완성하려 했는지, 무엇을 이미 사용했는지, 어떤 비교 자료를 찾았는지, 확인이 어려웠던 조건이 무엇인지, 결국 어떻게 결정했는지 묻는다. 실제 업무 자료는 필요한 범위만 받고 참가자가 공유 가능한 사례를 사용한다.

처음에는 선택 도움 12명/20명, 실제 사용 후 도움 확인 8명/20명, 28일 이내 의미 있는 재방문 6명/20명을 다음 실험을 논의할 내부 목표의 예시로 둔다. 시장 평균이나 성공을 보장하는 기준이 아니다. 작은 편의 표본의 비율이므로 반드시 인원수·미응답·구체적 사례를 함께 보고, 한 번의 통과만으로 대규모 개발을 결정하지 않는다.

| 지표 | 정의 | 해석할 때 주의할 점 |
|---|---|---|
| 선택 도움 | 비교를 제공받은 사람 중, 새로 시험·유지·전환·보류 결정을 기록하고 그 근거가 도움이 됐다고 응답한 사람 | 단순 저장과 클릭은 포함하지 않음; 사용자 자기보고 |
| 실제 사용 도움 | 비교 후 7일 관찰이 가능한 사람 중, 실제 업무에 사용했고 구체적으로 도움이 된 내용을 응답한 사람 | 만족 응답 수와 결과 사례 확보 수를 따로 표시 |
| 28일 의미 있는 재방문 | 첫 비교 후 1~28일에 비교·사용 결과·관련 변경을 확인하거나 갱신한 고유 사용자 / 28일 관찰이 끝난 참가자 | 뉴스 목록 방문만은 제외; 4주차 유지율과는 다른 지표 |
| 변경 정보 유용성 | 관련 변경을 실제 전달받은 사람 중 도움 됐다고 응답한 사람 | 전달 대상 수·응답자 수·도움 응답 수를 함께 표시 |
| 운영 유지 가능성 | 정해진 확인 기한 안에 점검한 필드 수 / 그 기간 점검 예정 필드 수, 운영 소요 시간 | 도구 수 확대와 함께 품질·비용 악화 여부 확인 |

미응답은 긍정 응답에 넣지 않고 별도로 센다. 관찰 기간이 끝나지 않은 참가자는 해당 기간 지표의 분모에서 제외한다. 참가자별 제공 날짜와 노출 여부를 기록해 비교를 받지 않았거나 변경이 없었던 사람을 잘못 평가하지 않는다.

초기 제품의 주간 핵심 성과는 ‘새로운 결정이나 사용 재검토에 도움을 받았다고 응답한 고유 사용자 수’로 제안한다. 신규 선택과 기존 선택 재검토를 별도로 집계하고, 같은 사용자의 반복 응답으로 수를 부풀리지 않는다. 저장률·페이지 조회수는 흐름을 진단하는 보조 지표로 사용한다.

**관찰 결과에 따라 다음 투자를 달리한다.** 선택 도움, 재사용, 커뮤니티 참여를 한꺼번에 성공 조건으로 묶지 않는다.

| 관찰 결과 | 다음 판단 |
|---|---|
| 비교는 유용하지만 재방문이 드묾 | 일회성 선택 가이드 수요를 더 검증하고, 업데이트의 관련성과 빈도를 다시 점검 |
| 내 도구 변경은 확인하지만 후기는 적음 | 내 도구함과 짧은 결과 기록을 개선하고 커뮤니티 확대를 늦춤 |
| 뉴스 반응은 있지만 선택 행동이 없음 | 뉴스 유입 대상과 도구 비교 대상이 맞는지 확인; 미디어 사업 가설은 별도로 평가 |
| 작업 방법을 반복 저장·공유함 | 업무별 실행 가이드와 공개 도구 조합을 우선 확장 |
| 정보 갱신 부담이 가용 시간을 초과함 | 등록 범위를 줄이고 핵심 도구의 확인 주기를 먼저 지킴 |
| 후보 선택 이후 실제 사용 도움이 적음 | 추천 규칙·평가 과제·대상 업무를 수정한 뒤 같은 규모로 재실험 |

**초기 유입 콘텐츠는 선택 상황이 제목에 드러나게 만든다.** 예시는 ‘한국어 조사 보고서: 출처 확인부터 내보내기까지 비교’, ‘현재 구독으로 가능한 문서 업무’, ‘이 업데이트 때문에 다시 테스트한 기능’이다. 콘텐츠마다 관련 업무 비교와 선택 저장으로 이어지는 행동을 하나씩 제공한다. 초기에 접근 가능한 직무 커뮤니티·동료 네트워크에서 협조 가능한 참가자를 모집하는 방안을 검토하되, 확인되지 않은 기존 네트워크나 확보 인원을 가정하지 않는다.

후기 공급은 운영진 테스트와 동의한 참가자의 실제 사용 사례로 시작한다. 도움을 준 비교 작성자와 질문의 맥락이 보이게 하여 다음 답변에도 참고할 수 있도록 한다. 기여자가 없어도 첫 사용 가치를 주는 편집 콘텐츠와, 참여가 늘수록 보강되는 경험 정보를 함께 운영한다.

**수익화는 반복되는 사용 이유를 확인한 뒤 실험한다.** 기본 탐색·평가 근거·기본 비교를 공개하고, 개인의 반복 관리 또는 팀의 공동 검토에 대한 지불 의향을 조사한다. 현재 가격이나 매출 전망을 확정할 근거는 없다.

| 수익 후보 | 유료로 제공할 가치 | 먼저 확인할 신호 |
|---|---|---|
| 개인 프리미엄 | 맞춤 변경 브리핑, 비교·선택 이력의 정리, 반복 업무별 추천 관리 | 무료 기능을 반복 사용하고 정기 관리에 비용을 지불할 의사가 있는가 |
| 팀용 | 공용 도구 목록, 공동 비교, 도입 근거 공유, 검토 기록 | 여러 명이 같은 도구를 검토하고 결과를 공유하는 문제를 겪는가 |
| 협찬·제휴 | 명확히 표시한 콘텐츠·행사 노출, 제휴 링크 | 관련 독자와 전달 가치를 확보했는가 |

유료 노출은 별도의 광고 영역에 표시한다. 광고·제휴 여부가 평가 점수와 일반 추천 순서에 영향을 주지 않도록 운영하고 그 원칙을 공개한다. 점수 상향이나 부정 후기 삭제를 상품화하지 않는다. 구매를 보류하거나 기존 도구를 유지하라는 결론도 제공하므로, 제휴 수익만으로 사업을 성립시킬 수 있는지는 별도로 확인해야 한다.

운영비에는 테스트용 구독·API 사용료, 정보 확인·재평가 시간, 콘텐츠·신고 처리, 서버·발송 비용을 포함한다. 월비용은 각 실제 비용과 운영 시간을 기록해 산정한다. 비교 1건 제작 시간, 주요 도구 1개의 월 유지 시간, 도움을 확인한 사용자 1명당 운영비를 추적하면 유지 가능한 범위를 판단할 수 있다.

**브랜드의 말투는 구체적인 근거를 설명하는 동료에 가깝게 잡는다.** ‘최고·압도적·무조건 추천’ 같은 단정 대신 ‘이 업무에 적합한 이유’, ‘이 플랜에서 확인한 범위’, ‘직접 테스트한 날짜’를 쓴다. 브랜드 가치는 실용성, 설명 가능한 평가, 정보의 최신성, 경험의 맥락이다.

AI Score라는 작업명은 평가 기능을 쉽게 연상시키지만, AI 생성 여부 판별이나 모델 성능 순위로 이해될 가능성이 있다. 실제 사용자가 어떻게 해석하는지 브랜드 테스트가 필요하다. 초기에는 이름 옆에 ‘내 업무에 맞는 AI·SaaS 선택 가이드’를 붙이는 안을 제안한다. 정식 이름은 도메인이나 권리 확보가 확인된 상태가 아니다.

**이번 제안에서 발전시킨 결정은 여섯 가지다.** 업무별 비교를 중심 경험으로 정하고, 첫 업무군을 좁히며, 선택 이유·사용 결과를 연결하고, 관련 변경으로 선택을 다시 검토하게 한다. 점수는 같은 작업의 조건과 근거에 연결하며, 커뮤니티 참여는 짧은 결과 기록부터 시작한다.

구현 전 확정할 결정은 핵심 사용자군, 첫 대표 업무, 운영자가 유지할 수 있는 도구 범위, 파일럿 모집 경로다. 이 문서는 그 결정을 검토할 수 있는 기준안이며, 상세 UI·데이터베이스·개발 일정·상용 요금은 후속 명세의 범위다.
